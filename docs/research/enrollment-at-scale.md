# Apple OTA Mail-Device Enrollment at Scale

**Status:** architecture design, 2026-11-27. Companion to [mail-device-binding.md](mail-device-binding.md) (sections 10–12).

**The problem.** Today, every step of Apple over-the-air (OTA) enrollment hits the API's single 10-connection Postgres pool (`apps/api/src/db/client.ts`), which is shared with the console, the sending API, and every webhook receiver (Clerk, Okta, SCIM, SES, Stalwart, Polar). Even an unauthenticated `GET /enroll/apple/<43-char-junk>` opens a Postgres transaction. A host-wide cap of 60 req/min and 8 in flight on `/enroll/apple/` was rejected as unacceptable, along with tuning workarounds that only push the cliff out slightly (raising caps, MAC-only token rejection while keeping per-request DB work, a second DB pool on the API, or per-token rate limits).

**Additional requirement (L4 promoted into scope).** Every `.mobileconfig` profile the device receives - Phase 1 (`Profile Service`), Phase 2 (SCEP-only), and Phase 4 (sealed final profile) - must be **signed** with a publicly trusted certificate issued and automatically renewed by the cluster's `cert-manager` (`letsencrypt-prod` via Cloudflare DNS-01), so iOS and macOS display the profile as **Verified** instead of a red "Not Signed" warning and red Install button, while keeping `enrolld` free of signing keys if possible.

**The goal.** Make enrollment cheap enough to survive both **internet floods** (unauthenticated HTTP, Apple-signed junk, SCEP junk, ACME junk) and **massive legitimate bursts** (many companies onboarding thousands of iPhones, iPads, and Macs simultaneously, including from behind shared corporate NATs), without every request costing a Postgres connection and without giving up the security invariants established in sections 10–12.

## Decisions (owner, 2026-11-27)

- **Architecture 3 is approved.** Stage 1 is built first: `enrollctl`, the dedicated Redis, signed links, local SCEP hooks in `cahookrelay`, one durable mint per device, and profile signing in `enrollctl` only.
- **Dedicated Redis (`i10-enroll-redis`), not the shared `i10-redis`.** An enrollment surge or flood must never fill the Redis that holds the email send queue, and enrollment state needs no disk.
- **The micro-batcher ships in Stage 1, from day one,** with tests for a bad row, a deadlock, a timeout and a partial batch.
- **Our own SCEP server (`scepd`, Stage 2) waits for measurement.** Stage 1 is load-tested first; step-ca is replaced for SCEP only if it is the measured limit.
- **Macs get our own stateless `device-attest-01` ACME server (owner's choice).** It replaces step-ca's ACME `apple` provisioner. Its temporary state (nonces, accounts, orders) lives in `i10-enroll-redis`, and it issues from the same device intermediate the mail front trusts, so the Mac's IMAP certificate path is unchanged. It scales horizontally with no shared file. It is new security-critical code: Apple's attestation verification and the ACME JWS checks must be reviewed hardest and proven on a real Mac before cutover. The alternatives it was chosen over were sharding step-ca by ACME path and step-ca on a shared SQL store.
- **One PR (owner's choice).** Stage 1, profile signing and the Mac ACME server ship together, built by agy and reviewed by the orchestrator plus an independent reviewer before merge.
- **Profile signing is proven on real devices** (section 3.4): a Let's Encrypt certificate shows "Signed by profiles.i10.tech" with the normal Install button on iOS 27.2 and macOS 27.3, for ECDSA P-256 and RSA 2048 alike.

#### Totals for a Single Clean Device Enrollment (Zero Retries, Zero Floods)

- **iPhone / iPad (excl. polling & notice):** **7 Postgres transactions (8 pool checkouts)**, **~71 SQL statements**, **~85 wire round trips**, **6 `lockGateAccount` (`core.mailbox_domain_refused`) calls**, 2 transient rows mutated 6 times across 15 combined indexes, 1 durable row (`authd.mail_devices`). **With 30 s of console polling:** **~38 pool checkouts and ~101 SQL statements.**
- **Mac (excl. polling & notice):** **8 Postgres transactions (9 pool checkouts)**, **~95 SQL statements**, **~111 wire round trips**, **9 `lockGateAccount` calls**, 3 transient rows mutated 8 times, 1 durable row inserted then updated. **With 30 s of console polling:** **~39 pool checkouts and ~125 SQL statements.**
- **Signing CPU added by L4:** Signing all 3 profiles adds **3 CMS `SignedData` signatures per device** (~3 ms CPU/device for RSA-2048, or ~0.15 ms CPU/device for ECDSA P-256). Crucially, signing must NEVER happen before authenticating an incoming request (otherwise an unauthenticated Phase 1 GET flood turns into a signing CPU DoS) and must NEVER run while holding Postgres locks.

#### Four Structural Wastes Exposed by This Audit

1. **Redundant work inside the current flow.** `scep-notify` runs a 12-statement locked transaction to write `issued_cert_sha256`, which `finish` never reads (Review 1 M2 explicitly forbids filtering on it) and whose errors step-ca discards (`scep/api/api.go:420`). `finish` calls `lockGateAccount` (and `SECURITY DEFINER` `core.mailbox_domain_refused`) **three times** inside one Mac transaction (`enrollments.ts:612`, `store.ts:254`, `permits.ts:300`) and performs RSA-2048/AES-256-CBC CMS encryption on Bun's single thread while holding DB row locks and a PgBouncer backend.
2. **Database-backed `peek` serves zero security purpose.** `GET /enroll/apple/<token>` returns a Phase 1 XML template containing only `profileURL` and the echoed `token`. It carries no account data and no secret; checking Postgres only provides a nicer 404 for expired/cancelled links at the cost of turning an unauthenticated GET into a direct DoS vector against the API's 10-connection pool.
3. **Transient state churns Postgres worse than durable state.** `mail_device_cert_permits` has **10 indexes** and transitions through 5 tuple versions in ~3 seconds (`open → challenged → authorized → notified → expired`), plus a 24-hour retention delete. `mail_device_enrollments` stores ~5–8 KiB of `sealed_profile` bytea (TOAST/WAL churn) purely to survive a ~10-second HTTP retry window.
4. **Non-DB ceilings sit immediately behind Postgres.** Even if Postgres were free, Traefik's current `i10-device-ca` middlewares (`infra/k8s/i10/device-ca/ingressroute.yaml`) impose **120 req/min host-wide** (~10 Macs/min or ~40 iPhones/min across all of i10!) and **30 req/min + 4 in flight per client IP** (~2–3 Macs/min for an entire company behind one corporate NAT IPv4!). And `step-ca` runs as **1 replica** (`Recreate`) because badgerv2 locks an RWO PVC.

Separating what **must** be durable in Postgres from what is only 15–30 minute protocol state reveals why Postgres is doing 8× more work than security requires:

### Architecture 1: Ephemeral State Store (Redis) + In-Pod SCEP Hooks + Single-Tx Durable Mint

**Core thesis.** Move all transient enrollment and permit state out of Postgres into a dedicated, diskless Redis instance (`i10-enroll-redis`), keep a fast outer HMAC on the link token so `enrolld` drops forged/expired floods in microseconds before touching any store or signer, render and CMS-sign all three profiles inside `i10-api` so `enrolld` stays key-less, evaluate SCEP webhooks locally inside `cahookrelay` against Redis, and shrink Postgres to one read-only start check plus one short commit at Phase 4 (and one at Mac Phase 5).

#### Why a Dedicated `i10-enroll-redis` Instead of Reusing `i10-redis`

`db-guard` (`references/redis.md`) sets a hard boundary: `i10-redis` (`maxmemory 384mb`, `maxmemory-policy noeviction`, AOF `everysec` + RDB) holds the **groupmq send and webhook queues**. Putting enrollment state in `i10-redis` creates two real hazards:

- **Memory blast radius:** Per active enrollment, session + SCEP hashes take **~1.2 KiB**, and the post-seal signed `sealed_profile` blob (M2, ~8–11 KiB once wrapped in CMS `SignedData` + chain) takes **~9–11 KiB**. A 10,000-device onboarding wave with 10-minute `sealed_profile` retention uses **~100–120 MiB** on top of Redis's RDB/AOF fork copy-on-write overhead. If `i10-redis` hits `384mb` under `noeviction`, **all customer email sending and webhook delivery fail with OOM**.
- **Unnecessary persistence cost:** `i10-redis` fsyncs AOF every second and snapshots RDB because queue jobs are product data. Transient 15-minute enrollment sessions need neither: losing an in-flight 30-second QR scan on a rare pod restart only asks the user to retry.

A dedicated diskless **`i10-enroll-redis`** (`redis:8.10-alpine`, `save ""`, `appendonly no`, `maxmemory 128mb`, `maxmemory-policy noeviction`, `256Mi` pod limit, no PVC, ~20 MiB RSS idle) isolates send queues completely, eliminates disk/fork overhead, and fits **~10,000 simultaneous enrollments** (or **~30,000+** if `sealed_profile` TTL is tightened from 10 min to 120 s, ample for an HTTP retry). Redis ACLs scope `cahookrelay` strictly to `enroll:scep:*` and `enroll:sess:*` read/refuse - never `enroll:sealed:*` or API keys.

_If `i10-redis` were reused instead,_ the strict requirements would be: mandatory atomic `SET ... EX` on every key (Lua script), `sealed_profile` capped at 90–120 s TTL, a hard cap on concurrent sessions (e.g., 4,000 → ≤45 MiB), and zero unauthenticated writes.

#### Profile Signing in Architecture 1 (Key Custody, Leak Containment, Hot Reload)

- **Key custody:** **`i10-api` alone** mounts `i10-profile-signing-tls` (`profiles.i10.tech`, read-only, mode `0440`, `fsGroup: 1001`). **`enrolld` holds NO signing key** and no CMS-signing code. Instead of rendering Phase 1 and Phase 2 profiles in `enrolld`, `i10-api`'s `/enrolld/peek` and `/enrolld/attest` render and sign them from fixed templates (using `ENROLL_PROFILE_URL` and `ENROLL_SCEP_URL` from `i10-api`'s own config) and return the signed DER bytes, just as `/enrolld/finish` already returns the complete Phase 4 profile.
- **Leak containment:** `enrolld` is internet-facing and parses untrusted bytes, yet a compromise of `enrolld` cannot steal the signing key **and cannot use `i10-api` as an arbitrary signing oracle** (the API never accepts raw plist bytes to sign; it only signs fixed `Profile Service`, SCEP, and `mail.i10.tech` templates). Conversely, `i10-api` already holds database credentials and `MAIL_DEVICE_CODE_KEYS`, so mounting the dedicated `profiles.i10.tech` signing key on `i10-api` adds no new privilege to an attacker who already owns `i10-api` - though it does mean an `i10-api` RCE also gets `profiles.i10.tech` (see section 3 for blast radius).
- **Zero-restart renewal:** Although `Bun.serve` cannot reload its own `:3443` TLS socket cert (`apps/api/src/ca-hooks/listener.ts:325`), the profile-signing cert is **not** a TLS listener cert - it is read by application code (`createProfileSignerLoader`, following the exact pattern of `createDeviceCaBundleLoader` in `apps/api/src/mail-devices/cms.ts:320-334`). On a 30-second timer (or `stat` `(mtimeMs, ino)` check), `i10-api` reads `tls.crt` (full chain) and `tls.key`, verifies that the leaf public key equals the private key and chains to the included intermediate(s), and swaps the in-memory signer atomically (keeping the previous valid signer on any mid-swap mismatch). No restart needed.

#### Security Properties

- **H1 (Phase 2 verification):** Unchanged. `enrolld` runs the exact same strict BER-to-DER CMS verifier, pinned expired Apple iPhone Device CA check, and flat plist parser. Phase 2 attributes remain unverified claims until Mac ACME `device-attest-01`.
- **H2 (Link token):** Preserved fully. The outer token `<v1>.<eid_hex>.<exp_hex>.<hmac16>` (~68 base64url chars) is verified by `enrolld` before any network call; Traefik keeps `observability.accessLogs: false` on `/enroll/apple/`; Phase 2 Lua binds `(serial, udid_sha256, apple_signer_sha256)` on first attest; post-seal notice email is queued via groupmq/worker after commit (`idempotencyKey: mail-device-enrolled:<deviceId>`).
- **H3 (SCEP without trusted i10 root):** Unchanged (`excludeIntermediate: true` in step-ca).
- **M1 (API seals & signs; `enrolld` never sees codes or signing keys):** Preserved and extended to L4. `enrolld` holds only `ENROLL_EDGE_HMAC_KEY` and `ENROLLD_API_TOKEN`.
- **M2 (Lost Phase 4 retryable):** Preserved. `finish` matches SCEP by `key_sha256` only and returns the cached signed+encrypted `enroll:sealed:<eid>` blob for repeat calls from the same key within its TTL.
- **M3–M7:** All preserved verbatim. Per-`(serial, clerk_user_id)` ACME permit (M6) becomes automatic because ACME permits are keyed by `nonce_sha256` (no global per-serial lock).
- **L1–L5:** All preserved verbatim, with **L4 satisfied** (all three profiles CMS-signed by `i10-api` with `profiles.i10.tech` + intermediate chain). Lock order (L3) shrinks to `authd.accounts → authd.mail_devices → authd.mail_device_cert_binds`.
- **Hold-vs-delete & mint-vs-revocation atomicity:** Unchanged. Phase 4 locks `authd.accounts` (`FOR NO KEY UPDATE`), checks `mintRefusal` + `expected_epoch` + `email` + `tenant_id`, and inserts `authd.mail_devices` in one transaction. Mac Phase 5 locks `authd.accounts` → `authd.mail_devices` and checks `bindRefusal` + `deviceKeyRefusal`.
- **Nuance on `cahookrelay` network boundary:** Because Kubernetes `NetworkPolicy` is pod-scoped, granting `i10-device-ca` egress to `i10-enroll-redis:6379` lets the pod reach Redis (though the Redis ACL password is mounted only into `cahookrelay`, identical to `CA_HOOK_TOKEN` today). Even if compromised, a SCEP ACL can only manipulate transient SCEP permits - never `authd.mail_devices`, `MAIL_DEVICE_CODE_KEYS`, or the profile-signing key.

#### Replay, Cancellation, Expiry, and Revocation

- **Replay:**
  - Phase 1 GET: idempotent until attest; forged/expired tokens die in `enrolld` (0 Redis, 0 API, 0 signing CPU, 0 DB).
  - Phase 2 attest: Lua checks `status == 'open'` or (`status == 'attested'` with identical `serial`, `udid_sha256`, `apple_signer_sha256`), enforces `now < created_at + 30m` (M4), deletes prior `enroll:scep:chal:<old>`, issues one new challenge.
  - SCEP: Lua atomically claims `enroll:scep:chal:<hash>` → `enroll:scep:key:<key_sha256>` + `enroll:scep:tx:<txId>` (`NX`); identical retries return `allow: true`, conflicting keys/txIds return `allow: false`.
  - Phase 4 finish: `authd.mail_devices.enrollment_id` partial unique index (`ON CONFLICT (enrollment_id) DO NOTHING`) guarantees **at-most-one device minted per enrollment in Postgres**, even if Redis restarts or loses a write between finish and cache-set. Repeat finishes from the same SCEP key hit `enroll:sealed:<eid>` in Redis without touching Postgres or re-signing.
  - Mac ACME: Keyed by `nonce_sha256` in Redis (TTL 10 min) + `acme_bound_at` on `authd.mail_devices`. A second key arriving within 10 min sees `status == 'authorized'` with a different key, locks `accounts → mail_devices`, clears `cert_key_sha256` (leaving `acme_bound_at` set so the row cannot be re-bound by a third request), deletes liveness rows, expires the Redis permit, and logs `ERROR`.
- **Cancellation:** `DELETE /console/mail-devices/enrollments/:id` (and starting a new enrollment via `POST`) runs a Redis Lua script that sets `status = 'cancelled'` and deletes the active `enroll:scep:chal:*` and `enroll:scep:key:*` entries. Subsequent Phase 1/2/3/4 requests fail immediately in Redis with 0 Postgres calls.
- **Expiry:** Enforced at two layers: checked in the signed outer token (`exp`) before any I/O, checked on logical timestamps (`expires_at`, `created_at + 30m`) inside Lua, and garbage-collected automatically by Redis key TTLs (eliminating `pruneMailDeviceEnrollments` and `pruneCertPermits`).
- **Revocation:** Any account hold, suspension, deprovision, or epoch raise during an in-flight enrollment is caught authoritatively at Phase 4 (`lockGateAccount` + `mintRefusal` + `expected_epoch`) and Mac Phase 5 (`bindRefusal`). Optionally, `raiseCredentialEpoch` / `endFor` can also delete `enroll:user:<uid>` in Redis for instant fail-fast UX, but **correctness never depends on Redis invalidation**.

#### Failure Modes

- **`i10-enroll-redis` restarts or crashes:** All in-flight enrollments vanish (**fail-closed**: no cancelled token can resurrect, no forged token can pass). Users with a QR on screen see 404/refusal and click "Try again." Already-minted devices in Postgres and active IMAP/SMTP sessions are 100% unaffected.
- **API crashes after Postgres `COMMIT` in Phase 4, before caching `sealed_profile` in Redis:** The device receives a 5xx and retries; `enroll:sealed:<eid>` is missing, Postgres `ON CONFLICT (enrollment_id)` prevents double-minting, so the retry is refused. The uncollected device code dies unused in 10 minutes (L2).
- **`i10-enroll-redis` hits `maxmemory` (`noeviction`):** New `POST /enrollments` fail with `503`; existing enrollments continue to finish and free memory; `i10-redis` (send/webhook queues) is completely untouched.
- **Profile-signing cert expires or fails to load:** `i10-api` logs at `ERROR` and fails closed (`503`) on `/enrolld/{peek,attest,finish}` rather than falling back to unsigned profiles (main `:3001` API stays up).
- **Postgres unavailable during Phase 4:** `finish` times out cleanly inside `SET LOCAL transaction_timeout = '4000ms'` and returns `503`; nothing minted.

#### Scaling and What Saturates First

- **Internet flood on `/enroll/apple/*`:** Dropped in `enrolld` by HMAC/exp (~100,000+ req/s per Go core). **Saturates first:** Traefik / host NIC. Zero signing CPU, zero Redis, zero API, zero Postgres load.
- **Internet flood on `/scep/apple-scep`:** `step-ca` must RSA-3072 decrypt the SCEP envelope before invoking `SCEPCHALLENGE`. **Saturates first:** `step-ca` CPU (~150–300 req/s on 1 core). Zero API, zero Postgres load.
- **Internet flood on `/acme/apple/*`:** Unauthenticated `new-nonce`/`new-account`/`new-order` writes unexpiring badgerv2 entries. **Saturates first:** `step-ca` 1 GiB badgerv2 PVC (unless host-wide ACME cap stays or badgerv2 is rotated). Forged/expired `finalize` hooks are rejected before Postgres.
- **Legitimate mass onboarding (e.g., 5,000 devices):**
  - `enrolld`: ~1,500–2,500 devices/s per core (horizontally scalable).
  - `i10-enroll-redis`: ~5–6 Lua ops/device → **~5,000+ devices/s** on 1 core.
  - **What saturates first for legitimate traffic:**
    1. **Traefik `i10-device-ca` caps** (120 req/min host-wide, 30 req/min per IP - corporate NATs choke first until raised/redesigned).
    2. **Single-replica `step-ca`** (~150–250 iPhones/s on SCEP RSA-3072; ~80–150 Macs/s on ACME `device-attest-01`).
    3. **`i10-api`'s single-threaded Bun event loop & shared 10-connection Postgres pool**: with RSA-2048 signing, **3 CMS signs per device = ~3 ms blocking JS crypto** (~300 devices/s hard single-thread ceiling, starving dashboard & sending HTTP latency!). Switching the signing key to ECDSA P-256 (if verified by device probe) drops signing CPU ~20×, leaving `i10-api`'s shared 10-conn pool (~150–300 finishes/s) as the bottleneck.

#### Changes Required and Migration

- **`enrolld`:** Add `ENROLL_EDGE_HMAC_KEY` verification (accepting versioned ~68-char signed tokens); relay signed Phase 1 & Phase 2 profile bytes returned by `/enrolld/peek` and `/enrolld/attest` instead of calling `RenderPhase1Profile`/`RenderSCEPProfile` locally.
- **API (`apps/api`), the superseded Architecture 1 plan (not built; section 6 "As built" is what shipped, and `cms.ts`, `enrollments.ts` and `permits.ts` are deleted):** Add strict DER `signCmsSignedData` + hot-reloading `createProfileSignerLoader` in `apps/api/src/mail-devices/cms.ts`; move Phase 1 & Phase 2 profile rendering + signing into `/enrolld/peek` and `/enrolld/attest`; sign Phase 4 after CMS encryption; replace DB calls in `enrollments.ts` and `permits.ts` with `i10-enroll-redis` Lua scripts; shrink `finishEnrollment` to 1 single-`lockGateAccount` tx using `SET LOCAL transaction_timeout` and move crypto outside the tx; queue notice emails for `i10-worker`; switch console `GET /enrollments/:id` to Redis/SSE; drop `/scep-*` handlers from `:3443`.

Teach `cahookrelay` to handle `/scep-challenge` and `/scep-authorize` locally in Go (porting `body.ts`'s SCEP template rules + Redis Lua calls), while continuing to relay `/acme-authorize` to API `:3443`.
- **Schema (`apps/api/src/db/schema.ts` + Drizzle migrations):**

- **Infra:** Add `i10-profile-signing` `Certificate` (`profiles.i10.tech`, `letsencrypt-prod`) mounted read-only into `i10-api`; add `i10-enroll-redis` Deployment/Service + NetworkPolicy + Doppler key `ENROLL_EDGE_HMAC_KEY`.

### Architecture 2: Stateless Self-Certifying Protocol (Cryptographic State Only, Zero Redis)

**Core thesis.** Eliminate **all** transient enrollment storage - neither Postgres tables nor Redis. Every protocol message carries its own AEAD-authenticated state forward inside the URL path, SCEP `Challenge`, SCEP certificate `OU`, and ACME certificate `OU`. Only a single `enrollment_epoch` counter on `authd.accounts` (plus `enrollment_id` uniqueness on `authd.mail_devices`) provides cancellation and single-use guarantees at the moment Postgres is finally touched.

#### Flow and Component Responsibilities

```text
Console (dash.i10.tech)
  POST /enrollments ──▶ API (:3001): 1 Postgres write tx (lockGateAccount + bump accounts.enrollment_epoch)
                        ──▶ seals T1 = header(v,kid,exp) || AEAD_K_api(eid,uid,tid,email,expected_epoch,enrollment_epoch,max_exp) || HMAC_K_edge
                        ──▶ returns https://ca.i10.tech/enroll/apple/<T1>
  DELETE /enrollments/:id ──▶ API (:3001): 1 Postgres write tx (bump accounts.enrollment_epoch if no mail_devices row with enrollment_id)
  GET  /enrollments/:id   ──▶ API (:3001): SELECT FROM authd.mail_devices WHERE enrollment_id = $1 (only detects `sealed`!)

Device ──▶ Traefik ──▶ enrolld (Go, holds K_edge + K_p2_sign; signing fork 2a vs 2b below!)
  Phase 1 GET /enroll/apple/<T1>:
    verify HMAC_K_edge + exp locally (~2 µs)
    ──▶ render & CMS-sign Phase 1 plist with URL = https://ca.i10.tech/enroll/apple/profile/<T1> AND Challenge = <T1>
        (2a: signed locally in enrolld; 2b: signed via stateless RPC to internal signer / API :3443, 0 Postgres!)
  Phase 2 POST /enroll/apple/profile/<T1> (Apple CMS):
    verify CMS + pinned Apple CA + plist + T1 == CHALLENGE + HMAC_K_edge + classifyApplePlatform locally (~1 ms)
    ──▶ mints:
        SCEP Challenge G = AEAD_K_scep(eid, serial, exp=min(now+10m, max_exp))   (~110 chars)
        SCEP Subject CN = <serial>, OU = P2Tag = compact_signed(eid, platform, product, udid_hash8, exp, HMAC_K_p2) (<=64 chars)
    ──▶ render & CMS-sign SCEP-only plist (2a: in enrolld; 2b: via internal template-locked signer, 0 Postgres!)
  Phase 3 SCEP ──▶ step-ca ──▶ 127.0.0.1:9443 cahookrelay (Go, holds K_scep, zero external I/O):
    /scep-challenge ──▶ decrypt G, check exp & CSR.CN == G.serial & OU matches G.eid; keep (key_sha256 -> serial, exp) in local Go LRU (~60 s)
    /scep-authorize ──▶ check template (CN, 1 OU, no SAN, emailProtection) + local Go LRU hit for key_sha256
    /scep-notify    ──▶ REMOVED
  Phase 4 POST /enroll/apple/profile/<T1> (SCEP CMS):
    verify CMS + Device CA chain + extract SCEP cert OU (P2Tag) ──▶ API (:3443) /enrolld/finish (T1, certDer, udid):
      1. verify certDer, decrypt T1, verify P2Tag MAC + eid/serial/udid match + now < max_exp (0 DB on forged/expired!)
      2. ONE Postgres tx: lockGateAccount; check mintRefusal + expected_epoch + account.enrollment_epoch == T1.enrollment_epoch;
         bump accounts.enrollment_epoch (burns T1!); INSERT INTO authd.mail_devices (..., enrollment_id) ON CONFLICT DO NOTHING
      3. AFTER COMMIT: for Mac, mint self-certifying 50-char ACME OU token = b64url(kid || device_id || exp || HMAC16(K_acme, ...));
         CMS-encrypt sealed_profile, wrap in CMS SignedData, enqueue notice email, return signed profile
  Phase 5 (Mac) ACME ──▶ step-ca ──▶ cahookrelay ──▶ API (:3443) /acme-authorize:
      1. template check + verify 50-char ACME OU HMAC + exp + serial match (0 DB on forged/expired!)
      2. ONE Postgres tx: lockGateAccount + lockDevice(device_id); check bindRefusal + deviceKeyRefusal + acme_bound_at logic;
         bind cert_key_sha256 + set acme_bound_at = now() (or clear on conflict, keeping acme_bound_at non-null!)
```

#### Profile Signing in Architecture 2 (The Architectural Tension!)

Because Architecture 2 eliminates backend calls in Phases 1 and 2, signing all three profiles forces a stark fork:

- **Option 2a - Mount `i10-profile-signing-tls` in `enrolld` AND `i10-api`:**
  - Keeps Phases 1 and 2 at zero backend RPCs (signing locally in Go inside `enrolld` with a 30 s `atomic.Pointer` file watcher + `tls.X509KeyPair` check, and signing Phase 4 in `i10-api` with `createProfileSignerLoader`).
  - **Major security regression:** **Violates `enrolld`'s zero-key rule.** Internet-facing `enrolld` parses hostile ASN.1/BER/XML from anyone on the internet; putting a publicly trusted `profiles.i10.tech` signing key into its pod means any compromise of `enrolld` gives the attacker a key that signs arbitrary "Verified" iOS/macOS profiles (rogue CAs, VPNs, proxies).
- **Option 2b - Keep `enrolld` key-less via a stateless internal signing hop (`i10-api:3443` or a tiny Go `profilesign` service):**
  - `enrolld` still drops forged/expired requests locally via `HMAC_K_edge`, then calls an internal template-locked signer RPC (`signPhase1(token)` / `signPhase2(serial, ou, challenge)`) with **0 DB and 0 Redis calls**. The internal signer renders and signs only hardcoded i10 templates (`ca.i10.tech` URLs) and hot-reloads `i10-profile-signing-tls` every 30 s (`atomic.Pointer` in Go or `mtimeMs`/`ino` loader in Bun).
  - **Cost:** Re-introduces an internal network hop on Phase 1 and Phase 2 (negating half of Architecture 2's zero-hop elegance) and either adds another service (`profilesign`) or puts Phase 1/2 signing CPU onto single-threaded `i10-api`.

#### Security Properties

- **H1 (Phase 2 verification):** Preserved. Strict CMS + Apple CA + plist checks run in `enrolld`.
- **H2 (Link token):** **Partially weakened.**
  - Traefik access-log suppression and post-seal notice email are preserved (note: `T1` now also appears in the Phase 2/4 URL path `/enroll/apple/profile/<T1>`, covered by the same `/enroll/apple/` router with `observability.accessLogs: false`).
  - **Gap:** Because Phase 2 has no shared store, a stolen QR code is **not** locked to the first device at Phase 2 - two devices can both complete Phase 2 and obtain SCEP certificates, and race to Phase 4. At Phase 4, Postgres ensures at most one mints a device, and the H2 notice email alerts the user if the attacker wins.
- **H3 (SCEP without trusted i10 root):** Preserved.
- **M1 (`enrolld` never sees codes / holds no keys):** Preserved for device codes; **broken for the profile-signing key under Option 2a**, preserved only under Option 2b. Note also that `enrolld` holds `K_p2_sign` and `K_scep`, so a compromised `enrolld` can mint SCEP grants directly (without needing `T1`!).
- **M2 (Lost Phase 4 response retryable):** **BROKEN.** With no transient store holding `sealed_profile`, a dropped HTTP response after Phase 4 commits cannot be retried because the plaintext device code is never stored. The user must restart enrollment, and the orphaned device code expires unused in 10 minutes (L2).
- **M3, M4, M6, M7:** Preserved (`max_exp = iat + 30m` is carried inside `T1`; Mac ACME `OU` token is per-device so two people sharing a Mac never collide).
- **M5 (One live enrollment per person):** Preserved via `authd.accounts.enrollment_epoch`: starting a new enrollment bumps the counter, invalidating any earlier `T1` at Phase 4.
- **L1 (Phase 4 signer):** Preserved, with one relaxation: `apple-scep.tpl` and L1 must permit **one `OU`** (`P2Tag`) alongside `CN` (still zero SANs, explicit `emailProtection`, no `clientAuth`, intermediate-issued).
- **L2, L3, L4, L5:** Preserved (L4 satisfied via Option 2a or 2b). Note that L3 adds an `UPDATE authd.accounts SET enrollment_epoch = ...` in Phase 0, Cancel, and Phase 4 - `enrollment_epoch` **must** be added to `authd.log_access_change`'s ignored columns so enrollment traffic never floods `authd.access_changes` or wakes `mailfront`.
- **Hold-vs-delete & mint-vs-revocation atomicity:** Preserved completely - Phase 4 and Phase 5 still lock `authd.accounts` and check `mintRefusal`/`expected_epoch`/`bindRefusal`.
- **Stolen `DEVICE_CA_INTERMEDIATE_KEY` offline:** Still cannot hijack an in-flight enrollment at Phase 4 unless the attacker also possesses `T1` and `P2Tag` (or `K_p2_sign`).

#### Replay, Cancellation, Expiry, and Revocation

- **Replay:**
  - Phase 1/2: `T1` can be replayed up to `exp` (15 min) / `max_exp` (30 min), capped only when Phase 4 commits.
  - SCEP: `cahookrelay` keeps a small in-memory bounded set of redeemed `G.nonce` values (TTL 10 min) so a single SCEP grant only issues for one keypair while `step-ca` stays up; a pod restart clears that set (acceptable because a second SCEP cert still cannot mint a second device at Phase 4).
  - Phase 4: **Strictly single-use** via `accounts.enrollment_epoch` check-and-bump + `UNIQUE (enrollment_id)` on `mail_devices`.
  - Mac ACME: 50-char `OU` token (`1B kid + 16B device_id + 4B exp + 16B HMAC16` = 37 B → 50 base64url chars) verified before Postgres; `mail_devices.acme_bound_at` prevents a third bind after a conflict clears `cert_key_sha256` (while `acme_permit_kid` or an operator flag prevents an unexpired token from undoing an operator's `bind-key`).
- **Cancellation:** `DELETE /console/.../enrollments/:id` locks `authd.accounts`, checks no `mail_devices` row exists for `enrollment_id` (else `409 already_sealed`), and bumps `enrollment_epoch`. Any cancelled `T1` fails at Phase 4 (though it is _not_ refused at Phase 1 or Phase 2 because those phases do not query Postgres).
- **Expiry:** Self-enforced cryptographically via `exp` and `max_exp` inside `T1`, `G`, `P2Tag`, and the ACME `OU`. Zero cleanup jobs.
- **Revocation:** Caught authoritatively at Phase 4 (`expected_epoch` + `mintRefusal`) and Mac Phase 5 (`bindRefusal`).

#### Failure Modes

- **Lost Phase 4 response (M2 regression):** Network blip between API commit and device breaks that attempt; user sees an error on device and must start over.
- **Console UX blindness:** Because Phases 1–3 never notify the API, the console cannot show `attested` (model/name) or immediate refusal reasons (`mac_not_apple_silicon`, `macos_too_old`, `unsupported_product`) - it can only show "waiting…" until either `mail_devices` gets a row (`sealed`) or the 15-minute client timer expires. Worse, polling `GET /console/.../enrollments/:id` against `authd.mail_devices` re-introduces **1,000 Postgres SELECTs/s per 1,000 onboarding tabs** unless a separate push channel is added.
- **Loss of `device_name`:** Arbitrary 128-char UTF-8 Mac names ("Mohamed's MacBook Pro") do not fit inside a single 64-byte X.509 `OU` alongside `eid`, `platform`, `product`, `udid_hash8`, and a 12–16 B MAC.
- **Protocol fragility on unprobed Apple behavior:** If iOS/macOS strips path suffixes or rejects dynamic Phase 1 URLs in Phase 4, or drops `OU` in SCEP CSRs, the entire design fails on real devices.
- **`authd.accounts` bloat:** Every enrollment start, cancel, and finish updates `authd.accounts` (a critical hot table read on every IMAP/SMTP login), generating dead tuples and vacuum churn on `authd.accounts`.

#### Scaling and What Saturates First

- **Internet floods:** Identical to Architecture 1 - forged `/enroll/apple/*` dies in `enrolld` (~100k+ req/s/core, zero signing CPU), SCEP floods hit `step-ca` RSA-3072 (~150–300 req/s), ACME floods hit `step-ca` badgerv2. Zero Postgres impact on floods.
- **Legitimate onboarding:**
  - **If console polls Postgres every 2 s:** `i10-api`'s 10-conn pool saturates first (~500–1,000 open tabs = 1,000–2,000 QPS).
  - **Without console DB polling:** `step-ca` single replica (~150–250 iPhones/s, ~80–150 Macs/s) and `i10-api`'s 10-conn pool (2 write txs per iPhone, 3 per Mac, all updating `authd.accounts` - plus Bun RSA signing CPU if Option 2b routes signing to `i10-api`) saturate around ~100–200 devices/s.

### Architecture 3: Dedicated Go Enrollment Plane + Micro-Batched Durable Commits + Stateless Go SCEP + Ephemeral Redis

**Core thesis.** Architecture 1 removes Postgres from floods and Phases 1–3, but leaves four ceilings intact under massive legitimate onboarding: (1) `i10-api`'s shared 10-connection pool and single-threaded Bun event loop still run Phase 4/5 and all profile-signing crypto; (2) `i10-api` still holds the profile-signing key beside `core.*`/`identity.*` DB credentials; (3) Postgres still pays 1 individual transaction, 1 `core.mailbox_domain_refused` call, and 1 WAL fsync per device; and (4) single-replica `step-ca` still sits in the critical path of every iPhone and iPad via SCEP.

Architecture 3 eliminates all four by introducing a dedicated internal Go service (**`enrollctl`**, shipped in the existing `i10-authd` image) that owns all profile rendering + CMS signing, transient Redis coordination (`i10-enroll-redis`), and a **synchronous micro-batching Postgres writer** (`pool_max_conns=2`, narrow `enroll_writer` role) - plus (in Stage 2) a **stateless Go SCEP responder (`scepd`) on its own enrollment-only CA**, leaving `step-ca` exclusively for Mac ACME `device-attest-01`.

#### Profile Signing in Architecture 3 (Key Custody, Leak Containment, Hot Reload)

- **Key custody:** **`enrollctl` alone** mounts `i10-profile-signing-tls` (`profiles.i10.tech`, read-only, mode `0440`).
  - **`enrolld` holds ZERO signing keys** (stays 100% faithful to its original untrusted-parser design).
  - **`i10-api` holds ZERO signing keys** (the main product API never even mounts the Secret).
  - **`step-ca` and `scepd` hold ZERO profile-signing keys.**
- **Leak containment:** `enrollctl` has **no internet ingress** (`NetworkPolicy` admits only `enrolld` and `i10-device-ca` on `:3443`). `enrollctl` renders and signs Phase 1, Phase 2, and Phase 4 from fixed templates using its own configured `ProfileURL`, `SCEPURL`, and `mail.i10.tech` - it never exposes a raw-bytes signing endpoint, so even a fully compromised `enrolld` cannot coerce `enrollctl` into signing a rogue root CA, VPN, or evil mail profile. And because `enrolld` drops forged/expired Phase 1 GETs via `ENROLL_EDGE_HMAC_KEY` before calling `enrollctl`, an internet flood causes **zero** signing CPU load on `enrollctl`.
- **Zero-restart renewal:** `enrollctl` uses the exact `atomic.Pointer` 30-second file watcher pattern already proven in `services/authd/internal/enroll/verify.go` (`DeviceCABundle.Watch`), `cmd/cahookrelay/relay.go`, and `cmd/mailfront` (`MAILFRONT_TLS_CERT_FILE`). On each tick (or mtime change), it reads `tls.crt` + `tls.key`, calls `tls.X509KeyPair` (which verifies the leaf public key matches the private key) plus checks leaf validity and intermediate chaining, and atomically swaps the pointer - keeping the previous valid signer on any mid-swap mismatch and logging at `WARN`/`ERROR` if expiry approaches. Multi-core Go signs **~1,000 RSA-2048** or **~20,000 ECDSA P-256** profiles/s per core across goroutines, never touching Postgres locks or `i10-api`'s Bun event loop.

_(Note: if the owner later wants the separate passwordless autoconfig profile at `GET /autoconfig/apple.mobileconfig` signed as well, `i10-api` can either make a tiny internal template-locked call to `enrollctl` or mount `i10-profile-signing-tls` read-only - the enrollment plane does not force `i10-api` to hold the key.)_

#### Deep Dive: Why Synchronous Micro-Batching Works Here Without Breaking Apple's HTTP Contract

Apple devices require a **synchronous** HTTP 200 `.mobileconfig` response to Phase 4 (and step-ca requires a synchronous `{"allow": true}` to ACME `AUTHORIZING`). You cannot return `202 Accepted` and process asynchronously.

Synchronous **group-commit micro-batching** inside `enrollctl` gives async-like Postgres efficiency with synchronous HTTP semantics:

1. **Zero penalty at low load ("costs close to nothing at 10"):** When the single writer worker is idle, the first arriving Phase 4 request dispatches immediately (`0 ms` batch wait) and commits in ~1.5–2 ms.
2. **Automatic coalescing under surge:** While batch #1 is executing (~4–10 ms), requests arriving during that window buffer into batch #2 (capped at `maxBatch = 200` or `maxWait = 5 ms`). At 1,000 devices/sec, batches naturally contain ~10–50 devices; at 5,000 devices/sec, ~100–200 devices - adding ≤5 ms latency to a multi-second human device enrollment.
3. **Massive amortization of `core.mailbox_domain_refused`:** When a company of 2,000 employees onboards on Monday morning, all 200 devices in a batch share the **same `(tenant_id, domain)`**. Evaluating `core.mailbox_domain_refused` once per distinct `(tenant_id, domain)` (using the exact `projection.SweepQuery` CTE shape proven in section 9 of `mail-device-binding.md`) cuts 200 `SECURITY DEFINER` calls down to **1**.
4. **Zero CPU crypto inside Postgres transactions:** Because `enrollctl` generates the `uuidv7()`, device code, HMAC, ACME `OU` token, inner CMS `EnvelopedData`, and outer CMS `SignedData` **in parallel across Go goroutines before entering the batcher**, a failed gate check simply drops that device's in-memory buffer and zeroes the code, while every accepted device holds Postgres locks only for the microsecond-scale SQL statements.
5. **Lock-order & deadlock safety (`db-guard/references/writes.md`):**
   - Accounts in the batch are locked via `SELECT ... FROM authd.accounts WHERE clerk_user_id = ANY($1) ORDER BY clerk_user_id FOR NO KEY UPDATE`.
   - Any single-account revocation locks 1 row, so it can never deadlock with a sorted multi-row batch.
   - A rare bulk revocation (`suspendWorkspace` / `suspendDomain` updating rows in heap order) could theoretically collide on `40P01`. The batcher catches `40P01` and retries (splitting into smaller chunks or single-row fallbacks on a second `40P01`) inside the 4-second deadline, ensuring correctness without losing a device.
   - On Mac ACME `AUTHORIZING`, the batcher locks `authd.accounts` (`ORDER BY clerk_user_id`), then `authd.mail_devices` (`ORDER BY id`), then deletes `authd.mail_device_cert_binds` - preserving global lock order L3 verbatim.

#### Deep Dive: Separating SCEP from `step-ca` (Stage 2)

In PR 3/4, SCEP and Mac ACME share the **same Device Intermediate CA** inside `step-ca`. That forced two heavy compromises:

1. Every SCEP certificate is signed by the CA that `mailfront` trusts for Mac IMAP `AUTHENTICATE EXTERNAL`, requiring strict EKU/no-SAN guards (L1) across both `apple-scep.tpl` and `mailfront` to prevent a SCEP enrollment cert from ever signing into IMAP.
2. Every iPhone and iPad enrollment depends on single-replica `step-ca` (`Recreate`, RWO badgerv2 PVC) and runs 3 synchronous webhook round trips through `cahookrelay`.

Moving SCEP into a stateless Go service (`scepd`) with its **own Enrollment-Only SCEP CA** (root + intermediate + RSA-3072 decrypter, **never** added to `mailfront`'s `MAILFRONT_DEVICE_CA_BUNDLE`) yields four simultaneous wins:

- **Stronger security boundary:** Even a complete compromise of `scepd`'s CA key cannot forge a Mac IMAP `EXTERNAL` certificate (`mailfront` does not trust that CA).
- **Zero `step-ca` dependency for iOS/iPadOS:** iPhones and iPads never touch `step-ca` or badgerv2 at all.
- **Horizontal scaling:** `scepd` has zero local disk state and scales to N replicas behind Traefik (handling 1,000+ SCEP enrollments/sec across 4–5 cores).
- **Zero webhook overhead:** `scepd` validates the SCEP challenge and binds `key_sha256` directly in `i10-enroll-redis` via one Lua script (using a narrow ACL on `enroll:scep:*` only) before signing the 7-day `emailProtection` cert.

_(Bonus flood shield in Stage 2: because `enrollctl` constructs the SCEP `URL` in Phase 2, adding a signed 10-minute path gate `/scep/<edge-hmac>/apple-scep` lets `scepd` drop forged SCEP `PKCSReq` floods in ~2 µs **before** spending ~3 ms on RSA-3072 decryption - subject to a 1-device probe verifying Apple's SCEP client preserves the dynamic path cleanly alongside `?operation=...`.)_

#### Security Properties

- **H1 (Phase 2 verification):** Preserved verbatim in `enrolld`.
- **H2 (Link token):** Preserved verbatim: outer HMAC token (~68 chars), Traefik access logs disabled on `/enroll/apple/`, Phase 2 first-attest binding in Redis Lua, post-seal notice email queued asynchronously via Redis/groupmq → `i10-worker` (`idempotencyKey: mail-device-enrolled:<deviceId>`).
- **H3 (SCEP without trusted i10 root):** Preserved (Stage 1 keeps `step-ca` `excludeIntermediate: true`; Stage 2 `scepd` serves the single decrypter cert DER as `application/x-x509-ca-cert`, verified by real-device probe before cutover).
- **M1 (`enrolld` never sees device codes, ACME nonces, or signing keys):** Preserved strictly. `enrolld` stays the isolated untrusted parser; `enrollctl` is internal-only (no internet ingress) and holds `MAIL_DEVICE_CODE_KEYS`, `i10-profile-signing-tls`, and `enroll_writer`.
- **M2 (Lost Phase 4 response retryable):** Preserved (`enroll:sealed:<eid>` in `i10-enroll-redis`, TTL 120–300 s; key-only matching; holds the complete signed+sealed DER bytes).
- **M3–M7:** All preserved verbatim.
- **L1 (Phase 4 signer):** Preserved in Stage 1; **strictly stronger in Stage 2**, where Phase 4 accepts ONLY the Enrollment-Only SCEP CA that `mailfront` never trusts.
- **L2, L3, L4, L5:** All preserved verbatim (**L4 satisfied** with zero signing keys in `enrolld` or `i10-api`; 2026-11-27 Mac 10-minute install grace and verified ACME `OU` kept).
- **Hold-vs-delete & mint-vs-revocation atomicity:** Preserved 100%. Every mint locks `authd.accounts`, checks `mintRefusal` + `expected_epoch` + `email` + `tenant_id`, and inserts `authd.mail_devices` atomically. Every Mac ACME bind locks `authd.accounts` → `authd.mail_devices` and checks `bindRefusal` + `deviceKeyRefusal`.
- **Least-privilege DB role (`enroll_writer`):** Unlike `i10_api` (which can read/write `core.*` and `identity.*` and `DELETE` devices), `enroll_writer` has ONLY:
  - `SELECT` on `authd.accounts`, `authd.managed_accounts`, `authd.passthrough_versions`, `authd.required_domains`, `authd.required_exempt`, `authd.mail_devices`
  - `EXECUTE` on `core.mailbox_domain_refused`
  - `INSERT` and `UPDATE (cert_key_sha256, first_used_at, last_used_at, acme_bound_at)` on `authd.mail_devices`
  - `DELETE` on `authd.mail_device_cert_binds`
  - Zero access to `core.messages`, `core.tenants`, `identity.*`, API keys, or billing.

#### Replay, Cancellation, Expiry, and Revocation

- **Replay:** Same strict guarantees as Architecture 1 (Redis Lua for Phase 2/SCEP; Postgres `UNIQUE (enrollment_id)` for Phase 4 single-use; Redis `enroll:sealed:<eid>` for M2 retries), **plus** Architecture 2's 50-char self-certifying ACME `OU` token (`device_id || exp || HMAC16`) + `mail_devices.acme_bound_at` so forged/expired ACME webhooks die in `enrollctl` with **0 Redis and 0 Postgres calls** while preserving full #536 key-conflict clearing and burn-after-conflict.
- **Cancellation:** Instant in `i10-enroll-redis` via Lua (`DELETE` or new `POST`); `enrollctl` checks Redis before Phase 4 enters Postgres, and `DELETE` returns `409 already_sealed` once sealed.
- **Expiry:** Outer token `exp` checked before I/O; logical `expires_at` & 30-min cap checked in Lua; automatic Redis TTL eviction (zero Postgres retention tables).
- **Revocation:** Authoritative at Phase 4 mint and Mac Phase 5 ACME bind under `authd.accounts` lock.

#### Failure Modes

- **`i10-enroll-redis` crash/restart:** Fail-closed for in-flight enrollments (users retry); zero impact on `i10-redis` send queues, zero impact on existing devices, zero chance of resurrecting a cancelled token.
- **Batch failure in `enrollctl`:**
  - Constraint/gate refusal for 1 device in a 200-device batch: **never** rolls back the other 199. Gate checks happen in Go after the locked read, before `INSERT`; `ON CONFLICT (enrollment_id) DO NOTHING` handles duplicate races per row without aborting the batch.
  - Transient DB error / `40P01` deadlock: retries whole batch once, then splits/retries inside the 4 s deadline; if Postgres is down, returns 503 cleanly and nothing is minted.
  - **Lost commit acknowledgement (as built).** A finish whose caller leaves while its job is still queued is never run (answered 503, nothing minted); once its job is in a transaction, the finish waits for the commit whatever its caller does, and seals the session and queues the notice under `context.WithoutCancel` (2 s), with up to 3 `SealSession` attempts (50 ms and 150 ms apart; the script overwrites, so a retry is idempotent), so a retry finds the sealed cache. Only the attempt that acquires `enroll:sealing:<eid>` (its random token, `SET NX EX 30`) mints; an attempt that does not acquire it answers from the sealed cache (same key: the profile; another key: `scep_key_conflict`) or 503 `seal_in_flight`, and never mints. The holder clears its own marker when it is done (compare and delete), including after a failed or refused mint, so the next attempt need not wait 30 s. A holder whose mint meets an already-minted enrollment with no sealed cache knows the earlier minter has finished and its seal was lost (Redis failed after the commit, on every retry): it refuses `enrollment_conflict` and marks the session refused, so the console tells the person to start again. **Residual:** that leaves an orphan `authd.mail_devices` row whose code was never delivered. It grants nothing, because nobody holds its code, and it is deleted automatically: the hourly retention run (`apps/api/src/mail-devices/prune.ts`) deletes never-used devices (`first_used_at IS NULL`) older than 10 minutes, so the orphan is gone within about 70 minutes. Until then it is visible in the console and can be deleted there.
- **Profile-signing cert renewal failure:** `enrollctl` retains the last valid certificate until expiry (30-day renewal runway with `renewBefore: 720h`), logs `WARN` on reload failure, and fails closed (`503`) if the active leaf expires rather than emitting unsigned profiles.
- **Notice email queue backlog:** Pacing notice delivery in `i10-worker` means a 10,000-device burst delays some notification emails by seconds/minutes rather than crashing `i10-api` or tripping SES 429s - and never blocks device sealing.
- **Single-replica `step-ca` rollout/restart:** In Stage 2, iPhones and iPads are **100% unaffected**; only Macs mid-ACME wait/retry during the ~5-second `Recreate` rollout.

## 3. Profile Signing (L4): Certificate Design, Blast Radius, Hot Reload, and Let's Encrypt Verification

All three OTA responses - Phase 1 (`Profile Service`), Phase 2 (SCEP-only `Configuration`), and Phase 4 (sealed `Configuration` with `EncryptedPayloadContent`) - are wrapped in DER-encoded RFC 5652 **CMS `SignedData`** (`application/x-apple-aspen-config`) carrying:

- the encapsulated XML plist (`id-data`) - for Phase 4, **encrypt-then-sign** (inner payloads already CMS-encrypted to the device's SCEP cert, outer XML plist wrapped in `SignedData`);
- a single `SignerInfo` (SHA-256 signature over `signedAttrs` containing `contentType`, `messageDigest`, and `signingTime`);
- the **full certificate chain** in `SignedData.certificates` (leaf + Let's Encrypt intermediate(s), e.g., `R10`/`R11` or `E5`/`E6`, which cert-manager already bundles into `tls.crt`), because iOS/macOS trust stores hold Let's Encrypt's root (`ISRG Root X1`/`X2`), not its rotating intermediates.

### 3.3 Zero-Restart Renewal

Kubernetes updates projected Secret volumes atomically via a symlink swap (`..data`), and `cert-manager` rotates `tls.crt` and `tls.key` together at day 60 (`renewBefore: 720h`, leaving a 30-day alert/recovery window). However, reading two separate files (`tls.crt`, then `tls.key`) across an atomic symlink swap can still observe the old cert with the new key.

The reload loop (Go `atomic.Pointer` in Arch 3 `enrollctl` / Arch 2a; cached `(mtimeMs, ino)` + 30 s timer loader in Bun/TS for Arch 1 / Arch 2b - independent of `Bun.serve`'s non-reloadable TLS listener):

1. Checks every 30 s whether the `tls.crt` + `tls.key` bytes changed.
2. Parses **all** PEM certificate blocks from `tls.crt` (requiring ≥2 blocks: leaf + at least one intermediate CA) and the private key from `tls.key`.
3. Verifies: (a) the leaf public key matches the private key (`tls.X509KeyPair` in Go; `X509Certificate.publicKey.equals(createPublicKey(privKey))` in Bun), (b) `now` is within `[leaf.notBefore, leaf.notAfter]`, and (c) `leaf` is signed by the included intermediate.
4. On mismatch (transient mid-swap read), retries once after 100 ms; if still invalid, **keeps the previous valid signer in memory** and logs `WARN`. Once verified, swaps the active signer atomically.
5. Emits a `WARN` log once remaining leaf lifetime drops below 14 days (alerting well before the 30-day renewal buffer runs out), and refuses to sign (`503`, never falling back to unsigned profiles) if the active leaf ever passes `notAfter`.

3. **ECDSA P-256 (`E5`/`E6`) vs RSA-2048 (`R10`/`R11`) CMS compatibility:** ECDSA P-256 is ~20× faster to sign (~0.05 ms vs ~1 ms), but we must verify that both iOS 27.2 and macOS 27.3 accept ECDSA CMS `SignedData` from our Go/TS signer (`smallstep/pkcs7` or strict DER encoder) with the `E5`/`E6` → `ISRG Root X1` chain.

## 4. Recommendation

**Adopt Architecture 3, rolled out in Stage 1 → Stage 2.**

### Why Architecture 3

1. **It actually removes the per-request DB cost - for both floods AND real onboarding surges.** Architecture 1 eliminates DB cost on floods and Phases 1–3, but still puts 1–2 synchronous Postgres transactions per device onto `i10-api`'s shared 10-connection pool and Bun's single JS thread. Architecture 3 gets enrollment off `i10-api` completely and amortizes even the one durable Postgres write per device across micro-batches on 2 dedicated least-privilege connections - preserving `i10-api`'s pool for the console, sending API, and webhooks regardless of how many companies onboard at once.
2. **Signed profiles (L4) fit Architecture 3 cleanly without compromising `enrolld` or overloading `i10-api`.** `enrollctl` is already the single internal, multi-core Go backend for Phases 1, 2, and 4 - so holding `i10-profile-signing-tls` in `enrollctl` alone keeps **both** internet-facing `enrolld` **and** `i10-api` completely free of the signing key, gives template-locked signing (no arbitrary-plist oracle), supports zero-restart `atomic.Pointer` hot-reload, and keeps signing CPU off Bun's single event loop. By contrast, Architecture 2 forces an ugly choice between breaking `enrolld`'s zero-key rule (2a) or re-adding backend RPCs on Phases 1–2 (2b).
3. **It keeps every security and UX property already earned in Reviews 1–5.** Unlike Architecture 2, it preserves M2 (`sealed_profile` retry on lost Phase 4), live console `attested`/`refused` visibility, Mac `device_name`, H2 Phase 2 device lock-in, and zero churn writes on `authd.accounts`, without betting on unprobed dynamic Phase 4 URLs or SCEP `OU` propagation.
4. **It uses the best piece of Architecture 2 where Apple already proved it works.** Using the 50-char self-certifying ACME `OU` permit + `mail_devices.acme_bound_at` (backed by L5, already verified on real macOS 27.3) removes ACME permits from both Postgres and Redis with zero risk.
5. **Stage 1 delivers 95% of the Postgres win immediately; Stage 2 cleanly unblocks iPhone/iPad CA scale.** Stage 1 keeps `step-ca` for SCEP (with local `cahookrelay` Redis hooks), shipping the full Postgres/API/signing decoupling with zero changes to the probed Apple SCEP wire format. Stage 2 then removes `step-ca` from iPhones/iPads and decouples the SCEP CA from `mailfront`'s Mac `EXTERNAL` trust anchor.
6. **Reuses existing Go assets.** `services/authd/internal/devicecode`, `internal/enroll`, `internal/gate`, `internal/projection`, and `smallstep/pkcs7` already live in `services/authd` with shared test vectors - putting `enrollctl` (and later `scepd`) in the `i10-authd` image adds zero new runtimes or build pipelines.

### Honest List of What This Recommendation Does NOT Solve

1. **Let's Encrypt EKU acceptance on iOS 27.2/macOS 27.3 (until probed) and 90-day post-install cosmetic badge expiry.** As detailed in section 3.4, if Apple rejects `serverAuth`-only Let's Encrypt leaves for `.mobileconfig` verification, `cert-manager` + `letsencrypt-prod` cannot solve L4 and a commercial/Apple-trusted signing cert is required. Even if accepted, already-installed profiles may show an expired signature badge in Settings after 90 days (cosmetic only; Mail and ACME keep working).
2. **Unauthenticated ACME `device-attest-01` floods against `step-ca`'s badgerv2 PVC.** Apple's `com.apple.security.acme` payload has no External Account Binding (EAB), and ACME requires `step-ca` to validate the exact JWS request URL against its own path - so we cannot cheaply pre-authenticate `/acme/apple/new-nonce` or `/acme/apple/new-account` at Traefik without replacing step-ca's ACME layer. Every unauthenticated `new-nonce`/`new-account` request still writes unexpiring keys to badgerv2. Mitigation remains a larger ephemeral volume / scheduled badgerv2 wipe (or migrating step-ca's ACME DB to an expiring store / upstream step-ca TTL fix) plus careful ACME-only Traefik rate limits.
3. **Mac ACME single-replica ceiling and corporate NAT rate limiting on `/acme/apple/`.** While iPhones and iPads scale horizontally past 1,000+/s in Stage 2, Apple silicon Macs still finalize ACME against 1 replica of `step-ca` (~80–150 Macs/s, plus ~5 s downtime on `Recreate` deploys). Traefik's current `30 req/min` per-IP middleware on `/acme/apple/` throttles a large office behind a single NAT IPv4 (~2–3 Macs/min); raising the per-IP limit improves corporate onboarding at the cost of making single-IP badgerv2 filling easier until badgerv2 expiry is solved.
4. **Downstream `mailfront` / `authd` first-connect storm.** Once 2,000 devices install their sealed profiles within seconds, all 2,000 Mail apps immediately connect to `mail.i10.tech:993` and `:465`. `mailfront` already bounds this via `MAILFRONT_MAX_PREAUTH=2000` (measured at 1.1 s p99 in section 9 of `mail-device-binding.md`), shedding excess connects cleanly for Mail to retry, and `authd` handles device-code lookups directly against Postgres - not solved by enrollment changes, though already engineered for storms.
5. **Notice-email (H2) SES throughput and `core.messages` write volume.** Queueing notice emails in `i10-worker` stops them from crashing enrollment, but onboarding 10,000 devices in 1 minute still creates 10,000 system emails competing for SES's per-second send quota and `core.messages` write budget (manifesting as delayed notification emails during massive surges).
6. **Traefik cluster-wide Secret RBAC.** As documented in `infra/k8s/i10/device-ca/README.md`, Traefik's cluster-wide RBAC still lets it read every Secret in `i10-prod` - including `i10-profile-signing-tls` once added. Narrowing Traefik's RBAC remains a separate `psl` repo fix.
7. **Stolen Device Protection ("Always") 1-hour delay (M4), Mac "two clicks" (section 5), and 3-year ACME re-enrollment.** Unchanged Apple platform constraints orthogonal to server architecture.

## 6. As built (I10-62)

This PR implements **Architecture 3 Stage 1 + profile signing (L4) + our own stateless Mac `device-attest-01` ACME server (`acmed`)**. Stage 2 (`scepd`, our own SCEP responder) stays out of scope; `step-ca` remains the SCEP CA on `/scep/apple-scep`.

### 6.1 Service split and `acmed` / `enrollctl` security boundary

- **`apps/api` (console + `enroll:notice` consumer):** `POST /console/mail-devices/enrollments` runs one read-only account/gate `SELECT` (zero locks, zero Postgres writes), allocates an RFC 9562 UUIDv7 `eid`, mints a signed edge link token, and writes `enroll:sess:<eid>` + `enroll:user:<uid>` atomically in `i10-enroll-redis` (cancelling any prior live enrollment, M5). `GET` and `DELETE` touch Redis only (0 Postgres queries). The link token is signed for creation + 30 minutes (the M4 hard cap) while the session itself must first attest within 15. `GET` also reads `enroll:scep:refusal:<eid>` and shows a live session with one as `refused`. A consumer group on the `enroll:notice` stream (created at `0`, so a notice written before the group exists is still sent) sends post-seal notification emails (H2) and `XACK`s only after send succeeds; `XAUTOCLAIM` reclaims crashed workers with an advancing cursor, and an entry delivered 10 times (XPENDING's count, read per reclaimed entry) is logged at ERROR and acknowledged unsent. The two enrollment secrets come from their own Secret `i10-api-enroll` (Doppler `prod_api_enroll`) by named `secretKeyRef`, never from `i10-api`, which the worker and CronJobs mount. The create and cancel Lua scripts are the same files Go embeds (`services/authd/internal/enrollredis/lua/`). The `:3443` listener, `apps/api/src/ca-hooks/*`, and profile/CMS/permit code are deleted from `apps/api`.
- **`i10-enroll-redis`:** Dedicated diskless `redis:8.10-alpine` pod (`save ""`, `appendonly no`, `maxmemory 128mb`, `maxmemory-policy noeviction`, no PVC, `default` user off) with 5 ACL users (`health`, `api`, `enrollctl`, `cahookrelay`, `acmed`), each starting from `-@all` and allowed only the commands its code sends (`users.acl.rules` in `infra/k8s/i10/redis/enroll-redis.yaml`; no `KEYS`, `SCAN`, `FLUSH*`, `DEBUG`, `CONFIG`, `ACL`, `MODULE`, `SCRIPT FLUSH|KILL`, `FUNCTION`, `EVAL`, `RESTORE`, `SORT`, `MIGRATE` or `INFO` for anyone). `services/authd/internal/enrollredis/acl_redis_test.go` loads those exact rules into a real Redis. Every enrollment key carries an explicit positive TTL (10m-1h; `enroll:notice` capped with `MAXLEN ~ 10000`). Redis errors and OOM fail closed (`503`).
- **`enrolld` (2 replicas, public `ca.i10.tech/enroll/apple/`):** Verifies the signed edge link token locally with `ENROLL_EDGE_HMAC_KEY` before acquiring a concurrency slot or calling `enrollctl`, dropping forged/expired links with zero internal traffic. Parses Phase 2/4 CMS `SignedData` and plists, calls `enrollctl /enrolld/{peek,attest,finish}`, and relays `enrollctl`'s already-signed Phase 1/2/4 CMS profile bytes verbatim.
- **`cahookrelay` (loopback sidecar in `i10-device-ca`):** Handles only `POST /scep-challenge` and `POST /scep-authorize` from `step-ca`. Validates webhook ID, 60s timestamp skew, and strict SCEP template rules locally and coordinates SCEP permits directly in `i10-enroll-redis` under the `cahookrelay` ACL: read and write `enroll:scep:*`, **read-only** `enroll:sess:*`, nothing else. Its refusals go to `enroll:scep:refusal:<eid>`. `/acme-authorize`, `/scep-notify`, and the API relay path are removed.
- **`acmed` (2 replicas, public `ca.i10.tech/acme/apple/`):** Keyless RFC 8555 `device-attest-01` server implementing directory, new-nonce, new-account, account and orders-list GET, new-order, order/authz GET, challenge POST, finalize POST, and cert GET. **Nothing an unauthenticated client sends writes Redis.** Its Replay-Nonces are stateless (`base64url(kid || random16 || exp || HMAC-SHA256[:16])` under `ACMED_NONCE_KEYS`, 5-minute life), and so are its accounts: an account is its key, and its URL (the JWS `kid`) is `<base>/acct/<base64url(canonical JWK)>.<base64url(kid || HMAC-SHA256(K[kid], "i10/acme-account/v1\x00" || kid || canonical JWK)[:16])>`, so `new-account` verifies the JWS, answers that URL and writes nothing, and a `kid` whose MAC does not verify is `accountDoesNotExist`. The account object (new-account and POST-as-GET on the account) is RFC 8555 7.1.2's: `status` `valid`, an empty `contact`, and the required `orders` URL `<account URL>/orders` (a real Mac on macOS 27.3 refused an account without it: "failed to establish account"). A POST-as-GET on that URL by its own account answers `{"orders":[]}`: accounts are stateless and nothing indexes orders by account, so the list is always empty; it spends no nonce and writes nothing. **Every URL is under a Mac's path token** (6.2): the sealed Phase 4 profile, CMS-encrypted to the Mac's SCEP key, names `https://ca.i10.tech/acme/apple/d/<token>/directory`, and only that Mac can read it. `acmed` verifies the token (key id, MAC, expiry) before anything else and with no Redis call; a missing, bad or expired token is a bare 404 with no Replay-Nonce. The directory and every link `acmed` returns stay under the same token, and the JWS `url` is checked against that per-request base. `new-order` must name the token's serial, and every order, authz, challenge and certificate records the token's device id and refuses a request under another device's token as well as another account's. The token replaces the old `enroll:acme:serial:<serial>` gate, which a serial (not a secret) opened for anyone: the gate let a stranger fill Redis with orders and spent nonces, use `new-order` as an oracle for the moment a Mac sealed, and exhaust the real Mac's order cap. **Nonce spend rule:** every JWS request checks its nonce statelessly. A read-only request (POST-as-GET on an account, its orders list, an order, authz, challenge or certificate, and a challenge response when the challenge and its order are already done) spends no nonce and writes nothing. A state change spends its nonce (`SET enroll:acme:used:<nonce> NX` for its remaining life plus a 60 s clock-skew margin) inside the one Lua script that makes the change, after every check that can refuse it: `new-order` in `acme_create_order.lua` after the device's order cap; a challenge response in `acme_answer_challenge.lua` after payload validation and the attestation check (pure CPU, in Go) and the pending and owner check (in the script); finalize in `acme_move_order.lua`, which claims the order `ready` -> `processing` after the CSR, subject and key checks and before `enrollctl` is called. A refusal writes nothing. **Every transition is one compare-and-set**, so of N concurrent requests on one order exactly one moves it, spends and (for finalize) calls `enrollctl`; the rest change nothing. A claimed order completes from `processing` only: to `valid` with its certificate (written in the same script), to `invalid` on a refusal, or back to `ready` when `enrollctl` is unavailable. A finalize that finds it `processing` gets `orderNotReady` with `Retry-After`, and a poll of it shows `processing` with `Retry-After` (RFC 8555 7.4). The order cap is per device id (`enroll:acme:dev_orders:<device_id>`, `ACMED_MAX_ORDERS_PER_DEVICE`, 20), so a re-enrollment (a new device id) gets a fresh cap. So with a valid path token Redis holds at most (devices sealed in the last 10 minutes) x (cap) orders, each with its authz, cert and the nonces its state changes spent, all living at most 10 minutes (each write keeps the object's remaining lifetime, never past the token's expiry), and nothing without one; an issued cert is served only to the account and device that finalized it (`enroll:acme:*` ACL only).
- **`enrollctl` (2 replicas, internal `:3443` only, hooks transport CA):** Renders and CMS-signs all Phase 1/2/4 `.mobileconfig` profiles with `i10-profile-signing-tls` (`profiles.i10.tech` ECDSA P-256 Let's Encrypt cert, hot-reloaded every 30s), encrypts Phase 4 inner payloads (AES-256-CBC + RSA PKCS#1 v1.5), commits `authd.mail_devices` inserts and Mac `cert_key_sha256` binds through a Postgres micro-batcher (up to 200 items or 5 ms, `enroll_writer` role, 2 connections/replica through PgBouncer, `transaction_timeout` 4 s (`lock_timeout` 2 s, `statement_timeout` 3.5 s)), and handles `POST /acme/finalize`.

**Security property of the `acmed` / `enrollctl` split:** `acmed` holds **no** CA private key, **no** permit key, **no** device-code key, and **no** Postgres credential. Its two keys mint nothing: `ACMED_NONCE_KEYS` MACs its own Replay-Nonces and account URLs, and `ENROLL_ACME_PATH_KEYS` (shared with `enrollctl`, which signs) verifies Mac path tokens. A forged path token only opens order creation for one serial; finalize still needs Apple's attestation of that serial and the OU permit. During the `device-attest-01` challenge, `acmed` verifies Apple's `x5c` chain and checks `OIDAppleNonce == SHA-256(challenge.token)`. When the Mac finalizes its order, `acmed` forwards `{serial, ou, csrDer, attestationX5c}` to `enrollctl POST /acme/finalize`. `enrollctl` independently re-verifies the Apple `x5c` attestation chain against the pinned Apple Enterprise Attestation Root CA, verifies the Apple serial extension equals `serial`, verifies the CSR signature, subject (`CN == serial`, single `OU == ou`, no other subject attributes or SANs), and that the CSR public key SPKI equals the attested leaf public key SPKI, verifies the 50-char Mac ACME OU permit (`ENROLLCTL_ACME_PERMIT_KEYS`), binds `cert_key_sha256` in Postgres (strict lock order: `authd.accounts FOR SHARE` through `authd.enroll_lock_gate_accounts`, then `authd.mail_devices` matching `device_id` and `serial`, then `authd.mail_device_cert_binds`), and signs the 1095-day leaf with `DEVICE_CA_INTERMEDIATE_KEY`. A full compromise of `acmed` cannot get a certificate for any key Apple did not attest for that serial, and cannot bind a key without a live OU permit that only the Mac received inside its encrypted Phase 4 profile.

### 6.2 Token formats

- **Edge link token** (`apps/api/src/mail-devices/link-token.ts`, `services/authd/internal/enrolltoken`): `v1.<32-hex-eid>.<hex-exp>.<23-b64url(kid(1) || mac16(16))>` (~68 characters total; MAC input is `"i10/enroll-edge-link/v1\x00" || kid || eid || uint64BE(exp)`). Both implementations are pinned against the same `services/authd/internal/enrolltoken/testdata/vectors.json`.
- **Mac ACME path token** (`services/authd/internal/enrolltoken/acmepath.go`): `base64url(kid(1) || deviceID(16) || uint32BE(exp) || serial(1..64) || mac16(16))`, MAC input `"i10/acme-path/v1\x00" || kid || deviceID || serial || uint32BE(exp)` under `ENROLL_ACME_PATH_KEYS`, expiry 10 minutes after the Phase 4 seal. The serial is carried in the token (not only covered by the MAC) so `acmed` can verify every request, including the directory and `new-nonce`, without a lookup.
- **Mac ACME OU permit** (`services/authd/internal/enrolltoken`): `base64url(kid(1) || deviceID(16) || uint32BE(exp) || mac16(16))` (50 characters exact, inside RFC 5280's 64-character OU ceiling; MAC input is `"i10/acme-ou-permit/v1\x00" || kid || deviceID || uint32BE(exp)`, and the device serial is enforced against `authd.mail_devices.serial` during the `enrollctl` micro-batched bind).

### 6.4 Schema, DB role, and load harness

- Dropped `authd.mail_device_enrollments` and `authd.mail_device_cert_permits`; added `enrollment_id` (unique partial index for idempotent Phase 4 commits) and `acme_bound_at` (for idempotent ACME replay) to `authd.mail_devices`. The `authd.mail_devices` access-change triggers ignore `enrollment_id` and `acme_bound_at` alongside `first_used_at` and `last_used_at`.
- `enroll_writer` is a CNPG-managed non-superuser role granted `SELECT` on the `authd` gate tables, `INSERT`/`UPDATE`/`SELECT` on `authd.mail_devices`, column-level `SELECT (device_id)` + `DELETE` on `authd.mail_device_cert_binds`, and `EXECUTE` on `core.mailbox_domain_refused`. The batcher locks `authd.accounts` with `FOR SHARE OF a` inside the SECURITY DEFINER function `authd.enroll_lock_gate_accounts(text[])` (every row-locking clause needs UPDATE privilege on a column, which `enroll_writer` must not have on `authd.accounts`; the row locks still belong to the batch's transaction and block a revocation `UPDATE`/`DELETE` until it commits), then writes `authd.mail_devices`, then clears `authd.mail_device_cert_binds`. The hold and route refusals come from `internal/gate` (`gate.Refusal`), the one copy authd's bind and the mail front use.

### 6.5 What a compromised `cahookrelay` can do

`cahookrelay` parses step-ca's webhook bodies, so treat it as able to send any command its ACL allows.

**It can hijack an enrollment that is in SCEP.** step-ca sends it every in-flight challenge in plaintext in the SCEPCHALLENGE webhook, so a compromised relay (or a compromised step-ca, in the same pod) can bind a victim's in-flight enrollment to its own key: `enrollctl`'s `checkSCEPBinding` cannot tell that binding from the device's, and the finish would return the victim's device code encrypted to the attacker's key. That is inherent to SCEP (whoever sees the challenge can use it), and was equally true before this change.

What the design does bound: a SCEP key binding carries the challenge plaintext step-ca sent, and `enrollctl`'s finish mints only when `sha256(binding.challenge)` is the session's **current** `scep_chal_hash`, the binding's session id is the session's, the binding's key is the Phase 4 certificate's key, and the session is `attested` and unexpired. So a party who can only write Redis (and never received a challenge) cannot bind anything. The relay cannot write a session (read-only `enroll:sess:*`), so it cannot attest one, change its challenge, serial or person, or touch a session that is not in SCEP; and it cannot reach `enroll:sealed:*` or any minted device. Beyond that it can refuse or stall enrollments (a refusal key, which is terminal, or a withheld `allow`). Because Redis checks every `EVALSHA` key for write access, the relay's scripts do not take the session as a key: the relay `GET`s it and passes its JSON as an argument. That read is not atomic with the claim, which is safe because the relay's verdict only lets step-ca issue a Phase 4 certificate, which grants nothing by itself.
