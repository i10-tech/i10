## 3. Top findings, ranked

### F1 (High) - The Okta tile for an OIDC app is refused

Okta's dashboard tile for an OIDC web app does a top-level GET to the app's "Initiate login URI" (third-party initiated login: `iss`, optional `login_hint`, `target_link_uri`). Our only matching URL is `/sso/<connection id>` (apps/auth/app/sso/[connection]/route.ts:27), which forwards to `/sso/start`. `startedByUs` (apps/auth/app/_lib/sso-server.ts:98-108) refuses any cross-site arrival whose Referer is not one of our origins, and Okta's tile arrives cross-site. Result: "Start your company's sign-in from i10." with no attempt and no audit. This is probably the same cause as the open FINDINGS bug "SSO start refused after arriving from the IdP's logout". `iss` is never read, `login_hint` is dropped by the tidy route, `target_link_uri` is ignored.
Fix: add a dedicated initiate-login endpoint (`GET /sso/initiate/<id>`) that is allowed cross-site, requires `iss` equal to the connection's issuer (OIDC third-party login rule, this is what makes it safe), keeps `login_hint`, ignores `target_link_uri`, and starts a normal attempt; show the same "continue as" confirmation SAML IdP-initiated uses if login CSRF is a concern. Give admins that URL in the Okta setup guide. Add a test with `sec-fetch-site: cross-site` and a foreign Referer.

### F2 (High) - SCIM refuses a bare token; the console tells the admin to paste it

`readToken` (identity/scim.ts:1302) requires `Bearer <token>`, and the test pins that a bare token is null (identity-scim.test.ts:1020). Okta's header mode on a custom SCIM app sends the field text as the Authorization header; only Okta's built-in SCIM connection adds `Bearer ` (UNVERIFIED on Okta's own pages; Sourcegraph's Okta guide and Okta's inbound SCIM page say the header carries the bearer scheme). The console says "Paste it into your provider as the SCIM bearer token" (directories-panel.tsx:135). An admin who pastes the token as shown gets 401 "A bearer token is required." from Okta's "Test connector configuration", and each try counts against the failed-auth limiter.
Fix: accept `i10_scim_...` with or without `Bearer ` (the prefix and 43-char shape make a bare token unambiguous), or at least print "Bearer i10_scim_..." in the issue dialog and in the Okta guide, and say which Okta field. Prefer both. Update the test.

### F3 (High) - Every SAML and OIDC verification failure gives the same words, and the console cannot explain them

`refusalMessage` (model.ts:304-331) maps `invalid_response` and most refusals to "We could not sign you in with your company's SSO. Ask your administrator." The reason for an Okta admin is only in the audit JSON (`data.failure`: `audience`, `destination`, `bad_signature`, `assertion_unsigned`, `signature_algorithm`, `expired`, `unsolicited_off`...). `wouldDo` (apps/console/lib/sso-runs.ts) has no entry for `invalid_response` or `idp_error` ("The provider's answer was not accepted."), and a refused test run is not recorded at all (FINDINGS: History still says "No test run yet"). So the exact moment Okta setup is most likely to go wrong (audience, ACS, signing options, certificate) is the moment the product says least.
Fix: (a) record a test-run row for every refused test sign-in, including verification failures, with the `failure` code; (b) add a code-to-sentence table with the Okta field to change ("Audience URI must be exactly <entity id>", "Set Assertion Signature to Signed with RSA-SHA256", "Untick 'Use this for Recipient URL and Destination URL' only if the Destination equals <acs>", "Clock differs by more than 2 minutes"); (c) show it on the test result and on the connection's health card; (d) keep the end-user text generic but add a reference id so the person can quote it. Same for OIDC (`invalid_client`, `redirect_uri` mismatch, `iss`).
F3b: with IdP-initiated off, an Okta dashboard click ends in the same generic text (`unsolicited_off`, saml.ts:671). Say so: when `failure` is `unsolicited_off`, show the owner a "Turn on IdP-initiated sign-in" prompt and tell the person "Open i10 and use Continue with Okta."

### F4 (High) - A renamed Okta login permanently locks a SAML user out

Subject is `persistent:<NameID>` (saml.ts:461-472) and the Okta preset asks for Persistent, but Okta's Persistent format carries the Application username (the Okta login by default), which an admin can rename and which "Update application username on create and update" rewrites. The bridge then finds no link for the new subject, finds the account through the address, and returns `already_linked` because the old subject still holds the user (bridge.ts:962-966). The person sees the generic text on every attempt until an admin deletes the link by hand. The preset comment calls this "refused, then claimed again by verified address" (saml.ts:456-458); the code does not do the second half when a link exists.
Fix (pick one, both are cheap): for the Okta preset recommend and default a `subjectAttribute` bound to an immutable Okta value (a custom attribute statement with the user's Okta id; Okta expression `user.id` UNVERIFIED), and show it in the setup guide; and give the admin a one-click "relink this person to the new subject" with step-up on the refused person's row, naming `already_linked` in plain words. Add a test for rename at the IdP.

### F5 (Medium) - NameIDPolicy Format is always sent and Okta requires it to match

`authnRequest` always emits `<samlp:NameIDPolicy Format="<preset>" AllowCreate="true"/>` (saml-messages.ts:96). Okta's own docs: if the request includes NameIDPolicy, the app's Name ID format must match it; Okta's wizard default is Unspecified while our Okta preset says Persistent (saml-presets.ts:114, :122). A mismatch ends at Okta (its error page) or an InvalidNameIDPolicy status that we show as "Your company's sign-in did not finish. Start again, or ask your administrator." The verifier already accepts persistent, email and unspecified (saml-verify.ts:498), so asking for one is not needed.
Fix: omit `Format` from NameIDPolicy for presets that cannot guarantee it (Okta, generic), or send the format the connection says it expects and keep the admin field authoritative; map `InvalidNameIDPolicy` to "Set Name ID format to X in your Okta app" in the F3 table.

### F6 (Medium) - Okta certificate rotation causes an outage unless the admin pre-adds the new certificate

Okta rotation is manual: generate an inactive certificate, give the SP the new one, then activate. The metadata URL shows the active certificate only (UNVERIFIED). We read the URL once a day behind a 20 h guard (saml-refresh.ts:37,148) and never on a signature failure; manual certificates are safe from the refresh (saml-store.ts:97-103). If the admin activates first, everyone is refused `bad_signature` with the generic text until the next nightly run or a manual "refresh" the admin does not know to press. The expiry alerts (30/7/1/0 days) help only for a certificate we already hold.
Fix: on a `bad_signature` or `no_usable_certificate` refusal for a connection with a metadata URL, trigger a rate-limited refresh (once a minute) and retry the verification once; raise a `sso.certificate.mismatch` alert to owners naming the connection; in the Okta guide say "add the new certificate here before you activate it in Okta".

### F7 (Medium) - Groups: custom servers and the 100 group limit

The `groups` scope is requested only when discovery lists it (oidc.ts:596-602). Okta's auth-servers page says custom scopes and claims are not returned in custom server metadata, so a custom server whose groups claim is bound to a `groups` scope sends no groups and every user becomes the default role without a word. The console has no Scopes field. Separately, Okta limits a groups claim to 100 groups.
Fix: add an editable Scopes field (already `config.oidc.scopes`), and make the test run show "groups: none received" next to the configured rules, with the Okta steps (Authorization server, claim, filter Matches regex, 100 group limit, use Starts with/Equals). Keep `scopesIfSupported`.

### F8 (Medium) - An unassigned or policy-denied user is told to "Start again"

On `error=access_denied` (and others) only the code is stored (oidc.ts:902-907) and the person sees "Your company's sign-in did not finish. Start again, or ask your administrator." Start again never helps for an unassigned user.
Fix: keep a sanitised `error_description` (truncated, no tokens) in the audit data; for `access_denied` say "Your company has not given you access to i10. Ask your administrator to assign you in Okta."

### F9 (Medium) - Step-up on Okta needs "Honor Force Authentication" and is untested

SAML step-up sends `ForceAuthn="true"` (saml-messages.ts:91) and relies on `AuthnInstant` being fresh (bridge.ts:1062-1068). Okta ignores ForceAuthn when the app's "Honor Force Authentication" is No, and the person gets the generic text. OIDC step-up on Okta is untested (FINDINGS), including whether the org server returns `auth_time` after `max_age=0`.
Fix: preset text for Okta says "Honor Force Authentication: Yes"; map `step_up_stale` to that instruction; run the step-up on a live Okta app more than 10 minutes after sign-in (FINDINGS asks for it).

### F10 (Medium) - Without SCIM, Okta cannot end an i10 session

SAML SLO is SP-initiated for Okta; OIDC back-channel from Okta is UNVERIFIED; Okta's Universal Logout is not implemented. Session limits default to null (db/identity.ts:81-83). A person unassigned or deactivated in Okta keeps an i10 session until Clerk expires it, unless SCIM deprovisions them.
Fix: say it in the connection page; offer a sensible default max session (for example 12 h) for Okta connections and show "SCIM not connected: removals in Okta do not reach i10" on a connection that has no enabled directory; consider the Universal Logout endpoint after reading Okta's page (not fetched here).

### F11 (Low) - Basic auth encoding is still not literal

Okta does not decode Basic credentials. `clientSecretBasic` form-encodes (oidc.ts:785-792), which only matches for secrets made of `A-Za-z0-9-_.*`, which is what Okta generates. A secret with `+`, `/`, `~` or a space (pasted from another system) is altered. Send the raw secret for the Okta preset, or make `client_secret_post` the Okta default.

### F12 (Low) - Our SP key rotation can break Okta "Signed Requests"

We sign with the newest SP key and keep one previous (saml-crypto, 2.16). Okta holds one uploaded Signature Certificate, so after our rotation signed requests fail validation until the admin uploads the new one. Rotate with an announcement step: show the new certificate, wait for "uploaded" confirmation, then switch signing.

### F13 (Low) - Group rename at Okta silently demotes

Rules match names exactly as sent (2.15). A rename makes the rule dead; admins become members at their next sign-in (owners untouched). The rules screen cannot show that no seen group matches.
Fix: record the groups of each sign-in (names only) and flag rules that matched nobody in the last N sign-ins, or offer the observed names when editing a rule.

### F14 (Low) - SCIM conflicts are invisible to the Okta admin

By design the push is answered with success (sso.md 2.17). An Okta admin sees green while the person is stuck on `domain_not_verified` or `no_sso_connection`. Keep the design, but put a count of conflicting people on the directory card and in the weekly summary email to owners, and mention it in the Okta SCIM guide.

### Other notes

- Okta preset `requires` (saml-presets.ts:122-127, oidc-presets.ts:93-101) does not list: Single Logout fields, Honor Force Authentication, IdP-initiated tile, "metadata URL: Sign On tab", the 100 group limit, header token with `Bearer `. Add them when the setup guide is built.
- SAML `login_hint` through `Subject/NameID` on Okta is unverified.
- A linked sign-in does not update the Clerk address when Okta changes the email (only SCIM does, directory.ts:402-427).

## 4. Where we are already strong (do not touch)

Path-less PATCH, group member filters, 409s, case-insensitive filters, 201/Location, stable pagination and Okta's id-in-value rename are all in and tested. Okta OIDC specifics are handled (userinfo for `email_verified` and names, `groups` scope only when listed, Basic encoding, private_key_jwt audience). SAML verification is strict and well covered (signature position, algorithms, audience, recipient, replay, skew, encryption).
