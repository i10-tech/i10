## 3. Top findings, ranked

Severity is for an Entra customer following Microsoft's docs and our own setup guide.

### F1. High: Entra OIDC step-up probably always fails (`auth_time` is an optional claim)

D7 lists `auth_time` as an optional claim, not a default v2 ID token claim. Our step-up (oidc.ts:~490 `prompt=login`, `max_age=0`) then refuses with `step_up_stale` whenever `auth_time` is absent (bridge.ts:1062-1068), and the Entra preset `requires` list (oidc-presets.ts:108-114) never tells the admin to add it. Every sensitive console action by an SSO-signed-in managed admin on an Entra OIDC connection would loop. Fix: add `auth_time` to the Entra preset's required optional claims and to the setup guide; for the `entra` preset only, accept `iat` as the authentication time when the request carried `prompt=login` and `auth_time` is absent (Entra honours `prompt=login`, D8, so `iat` is within seconds of the re-auth; do not do this for other providers); add a test-run check that reports "auth_time missing, step-up will fail".

### F2. High: no group overage handling; silent role loss

Entra drops the `groups` claim above 150 (SAML) or 200 (JWT) groups and substitutes `groups.link` or `_claim_names` (D6). Nothing in the code or design record mentions it (no `groups.link`, `_claim_names`, `hasgroups`). A person with many groups is resolved with groups = [], gets `member`, and a group-rule admin is reset to member on the next sign-in (roles are re-read every sign-in, bridge.ts rules block, jit.ts:46-62). Fix: detect the overage markers in both protocols, mark the assertion `groupsIncomplete`, and in that case keep the person's current role (no demotion, no promotion), record `sso.groups_overage` in the audit log, and show it in the test run ("this person is in too many groups; filter the claim to groups assigned to the application"). Optional later: fetch groups via Graph with an app permission. Also add group claim instructions to both Entra presets (groups assigned to the application, GUIDs; `groupMembershipClaims` for OIDC).

### F3. High: the shareable sign-in link and My Apps Sign-on URL cannot work

`GET /sso/<connection id>` ("the link an admin gives their team", apps/auth/app/sso/[connection]/route.ts) redirects to `/sso/start`, which returns "Start your company's sign-in from i10." for any request whose `Sec-Fetch-Site` is `cross-site` (apps/auth/app/_lib/sso-server.ts:98-108; start/route.ts:25). A click from Entra My Apps, Outlook on the web, Slack or a wiki is cross-site, and a redirect chain keeps the initiator's site. Only typed URLs and bookmarks pass. IdP-initiated sign-in is off by default (saml.ts:671-674), so the Entra tile has no working path at all. (Verify in a real browser; Fetch Metadata is recomputed against the full redirect chain.) Fix: make `/sso/<id>` render a small same-site page with a "Continue to <company> sign-in" button; the click is a same-origin navigation to `/sso/start`, so the login-CSRF defence (a user gesture on our own page) is kept. Document it in the Entra guide as the Sign-on URL, and tell the admin to either set the Sign-on URL or turn on IdP-initiated sign-in.

### F4. Medium-high: end-user and admin errors give no next action, and AADSTS detail is thrown away

`refusalMessage` (model.ts:304-332) collapses `no_email`, `email_unverified`, `domain_not_verified`, `already_linked`, `managed_elsewhere`, `ambiguous_account`, `step_up_*` and every `invalid_response` into "We could not sign you in with your company's SSO. Ask your administrator." The admin has nowhere to read the cause except the audit log or a test run, and console/lib/sso-runs.ts has no entry for the SAML/OIDC `failure` subcodes (`assertion_unsigned`, `bad_signature`, `issuer`, `audience`, `no_usable_certificate`, `unsolicited_off`...). For Entra, the OIDC `error_description` (AADSTS text, oidc.ts:860-869) and the SAML `StatusMessage` (saml-verify.ts:217-222) are discarded. Fix: (a) keep a sanitised `AADSTS\d{4,6}` token (regex-only, never free text) from `error_description` and `StatusMessage` and store it in `extra`; (b) give each refusal and each verify failure a console explanation with the Entra-specific remedy (e.g. `email_unverified` on an entra connection: "Add the optional claims email and xms_edov"); (c) show the last refusal reason and failure code on the connection page (also the open FINDINGS item about dead-end test runs); (d) keep the end-user text generic but add "Your administrator can see why in the SSO settings" so the person has a next step.

### F5. Medium: SAML email has no fallback for Entra users with an empty `mail`

Cloud-only Entra users commonly have no `mail` value, so the `emailaddress` claim is omitted (D2: the default claims include user.mail; a null source is not emitted). saml.ts:520-521 falls back only to a NameID that is an email (and the Entra preset asks for persistent), so the person gets `no_email`. SCIM does fall back to `userName` (scim.ts primaryEmail), so the same person can be provisioned and still fail to sign in. Fix: for the entra preset, fall back to the `.../claims/name` (UPN) attribute when it parses as an address; the existing live-domain proof limits the risk. Mention "give users a mail value or keep the default `name` claim" in the guide.

### F6. Medium: Entra-initiated SLO is probably rejected twice

D5: Entra sets the Issuer of its logout messages to `https://login.microsoftonline.com/<tid>/`, while our stored entity id is the sign-in issuer `https://sts.windows.net/<tid>/`. readLogoutRequest requires an exact match (saml-messages.ts:304) and also refuses an unsigned redirect-binding request (:239). D5 does not say Entra signs the request, and field reports say it does not (unverified). Net effect: a person who signs out at Entra keeps their i10 session, and the admin sees only `logout.failed` in the audit log, although the preset tells them to configure the Logout URL (saml-presets.ts:134). Fix: (a) for entra connections accept either issuer form (`sts.windows.net/<tid>/` or `login.microsoftonline.com/<tid>/`); (b) decide on unsigned requests: an optional per-connection "IdP does not sign logout requests" setting that accepts them only when the SessionIndex (unguessable) names one of our bound sessions; (c) probe against a real tenant first. Same issuer-form leniency should be considered for the sign-in assertion (saml-verify.ts:482), because the doc's own sample shows `login.microsoftonline.com` (S8).

### F7. Medium: certificate rollover relies on the nightly job

D4: admins create a new cert, then "Make certificate active"; Entra recommends the SP pick the new key up from metadata beforehand. We poll once a day with the recheck job. Same-day activation means up to a day of failed sign-ins. Fix: on `bad_signature` or `no_usable_certificate` for a connection with a metadata URL, enqueue a metadata refresh (rate limited to one per 10 minutes per connection) and retry the verification once; also add "use the App Federation Metadata Url (with `appid=`), not the tenant-level URL" to the Entra guide (S11).

### F8. Medium: no OIDC client secret expiry tracking

Entra secrets expire (default six months in the portal, at most 24, D9 context). Today the only symptom is `invalid_client` at the token endpoint and a health "failing" state. Fix: optional `secretExpiresAt` the admin enters (or defaults to a 6/12/24 month choice) with the same 30/7/1/0 day alert path used for SAML certificates (alerts.ts, saml-refresh.ts), and a clear health message "the client secret was refused; it may have expired".

### F9. Medium: SCIM filter and token gaps Entra documents

(a) D11: when the matching attribute is `emails[type eq "work"].value`, Entra queries `emails[type eq "work"].value eq "x"`; we return 400 `invalidFilter` and a unit test pins the refusal (identity-scim.test.ts:111, scim.ts:243). D11 also says Entra uses `and`. Fix: accept the bracketed email form (equivalent to `emails.value` with a type check) and `and` of two supported `eq` terms. (b) 401 for unknown, revoked and expired tokens all say "The token is not valid." (routes/scim.ts:202-210); Entra shows that text in the provisioning log. Fix: for a token we know, say "The token expired on <date>. Issue a new token in i10 and paste it into Entra's Secret Token." / "The token was revoked.". Revealing this to the holder of a once-valid token leaks nothing new. (c) No alert before a SCIM token expires and none when a directory stops syncing (Entra normally calls about every 40 minutes, K). Fix: alert at 7/1 days before `directoryTokens.expiresAt` and "no calls for 6 hours" on the directory page. (d) `POST /Groups` has no 409 for a duplicate displayName, which the Entra validator checks (D11); minor.

### F10. Medium-low: Entra OIDC guide and claim gaps

The Entra preset says to add `email` and `xms_edov` (good) but not `given_name`, `family_name`, `auth_time` (F1), `groups` (F2), the need for admin consent when user consent is off, or "Assign users and groups". Two small code risks: `xms_edov` is accepted only as `true`/`"true"` (oidc.ts:723; make `1`/`"1"` count); and the userinfo fallback (oidc.ts:630-660) will silently give up if Graph's `sub` differs from the ID token `sub` (unverified, probe). Fix: update the Entra requires list, probe both behaviours against a real tenant, and fall back to splitting the `name` claim only if you decide a name guess is acceptable (decision 2.15 says no, so keep refusing).

### F11. Low-medium: stable identifiers

OIDC `sub` and SAML persistent NameID are per-application pairwise values (D1, D6). Recreating the Entra app registration or enterprise application changes them all; plain members are reclaimed by verified address, managed owners/admins are not (sso.md 2.14), so the owner is locked out until another owner relinks. Option: for the `entra` presets use `tid:oid` as the subject (D6 says `oid` + `tid` is the stable pair), via an Entra-only exception to "the mapping cannot change `sub`" (oidc.ts:687-690) and a `subjectAttribute` default of the `objectidentifier` attribute for SAML. Otherwise, add a console warning "do not recreate the app; see how to relink".

### F12. Low-medium: no front-channel or RP-initiated logout for Entra OIDC

Entra supports front-channel logout only (D8). We implement back-channel logout only (oidc-logout.ts), and no RP-initiated logout (FINDINGS open bug). A person who signs out of Entra, or an admin who disables them, keeps their i10 session until the connection's session limits. Fix: add `GET /sso/frontchannel-logout/<connection>?sid=&iss=` that revokes sessions bound to that `sid` (requires `frontchannel_logout_session_required` on the app registration), and document the session limits as the backstop; SCIM deprovisioning is the real control.

### F13. Low: UX gaps

Login hint is not sent to Entra SAML (S4: append `login_hint=` to the SSO URL; it is allowed there per D1, unlike a Subject element, and must be added before the redirect signature is computed, saml-messages.ts:redirectUrl). Issuer entry accepts only lowercase GUIDs and the error does not say why `common`, `organizations`, domain names and sovereign clouds are refused (O2, O3). SCIM `domain_not_verified` rows leave Entra showing success (C21).

### F14. Low: SAML issuer exactness

saml-verify.ts:482 compares the assertion Issuer to one stored string. D1's text says `https://sts.windows.net/<tid>/`; its sample shows `https://login.microsoftonline.com/<tid>/`. If Microsoft moves tenants to the second form, every Entra SAML sign-in fails `issuer` with the default text. Consider an entra-only allow-list of both forms derived from the tenant id (the same tenant id, so no weaker trust).

## 4. What is solid (verified in code)

- Entra PATCH dialect (capitalised ops, string booleans, path-less value objects, filtered email path creation, member removal by value list) is implemented and tested (scim.ts:417-424, 545-553, applyAt/applyFragment; identity-scim-routes.test.ts:779, 805, 994-1033).
- Test-connection probe, soft delete/restore, 409 on duplicate userName, `excludedAttributes=members`, discovery endpoints, `aadOptscim062020` tolerance.
- SAML requests avoid every field Entra rejects (Subject, SPNameQualifier, Scoping, RequestedAuthnContext).
- Encrypted assertions (AES-CBC + RSA-OAEP) and signed-request support match what Entra sends and verifies.
- OIDC issuer pinning to the tenant, rejection of `common`/`organizations`, `sub` as identity, email only as a claiming hint behind a live proved domain and `xms_edov`.
- Replay protection, binding cookie, assertion-signature-only trust, and certificate expiry alerts.
