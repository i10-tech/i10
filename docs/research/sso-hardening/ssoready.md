# SSOReady, read against our SSO hardening list

Read 2026-11-02. Clone: `src/ssoready` (shallow, never run or installed). All paths below are relative to that clone. Nothing in /Users/mohamedabdulkhalek/i10 was edited.

Headline: SSOReady is a much smaller and weaker engine than ours. Its SAML verifier is a hand-rolled, assertion-only, single-certificate, RSA-SHA256-only check with no clock skew, no Destination or Recipient check, and no logout. Our verifier (`saml-verify.ts`) is ahead on almost every protocol point. What it does have, and we should borrow, is the operator experience around failures: typed failure records, an error page that shows Expected vs Actual and says who must fix it, a per-attempt flow view with the raw assertion, a SCIM request log, and a wizard that ends in a real test login.

## 1. What it is and its state

- Open-source (YC W24) "SAML and SCIM as a service": a Go backend, plus a hosted customer admin portal ("self-serve setup UI"), plus a developer dashboard, plus client SDKs in 7 languages (`README.md:1-40`). The host app never parses SAML: it redirects to SSOReady, then redeems a `saml_access_code` over an API to get the verified email and attributes.
- License: MIT, "Copyright 2024 Codomain Data Corporation (dba SSOReady)" (`LICENSE:1-3`). Copying ideas is free; copying code is allowed with the notice.
- Size: about 35k lines including generated code. Go in `internal/`, React in `app/` (developer dashboard) and `admin/` (customer portal).
- Activity: last commit on main is 2025-08-28 ("Support email.value filter in SCIM user list endpoint", #266). Only 14 commits since March 2025, and the last 5 are logging tweaks and small SCIM fixes. The repo shows no commit for 14 months as of today. GitHub reports not archived, 1,531 stars, 3 open issues. Verdict: alive but in maintenance mode, run by one small company as a hosted product. Do not depend on it for protocol fixes.
- Architectural difference that matters: SSOReady's identity key is the NameID, which must be an email on an allowed organization domain (`internal/authservice/service.go:294-315`). It stores no persistent per-user identity. That is why it never meets our "changed subject" dead end, and also why it cannot be a model for our identity model.

## 2. Our hardening README, item by item

Legend: SOLVED (they handle it), PARTIAL, NOT (they do not, or they do it worse), N/A (different architecture).

| # | Our item | SSOReady | Where and how |
|---|---|---|---|
| 1 | Changed subject dead end | N/A | Identity is the email in NameID, re-derived every login (`service.go:294-303`), no stored subject to go stale. Nothing to learn for relink; do not copy, our subject model is correct. |
| 2 | Starts from outside our sites | PARTIAL | SAML IdP-initiated works by construction: the ACS accepts an assertion with empty InResponseTo, skips the replay-by-flow check (`store/auth.go:193-196`), and mints a fresh flow id (`store/auth.go:268-276`). The login then ends in a redirect to the customer app carrying a one-time code (`service.go:494-508`). No Referer logic exists. No OIDC at all. Idea for us: the SAML path needs no same-site Continue page; confirm ours already treats a response with no InResponseTo as a new flow, and keep the same-site page only for OIDC third-party initiated login. |
| 3 | Missing group data demotes people | NOT | SAML attributes are flattened to `map[string]string`, so a multi-valued `groups` attribute collapses to its last value (`internal/saml/validate.go:139-142`). SCIM groups are real objects. Do not copy. |
| 4 | Directory pull deprovisions people who exist | N/A | Push SCIM only, no pull. |
| 5 | MFA settings that cannot be satisfied | NOT | No MFA, step-up, or AuthnContext handling anywhere. |
| 6 | SCIM token pasted without `Bearer ` | SOLVED, trivially | `strings.TrimPrefix(Authorization, "Bearer ")` accepts both forms (`authservice/scim.go:955`, `scim.go:1024`). The token itself is a prefixed id whose SHA-256 is stored (`store/auth_scim.go:59-65`). Copy the behaviour: strip the optional scheme, then check the `i10_scim_` prefix. |
| 7 | We always ask NameID format persistent | SOLVED by omission | The AuthnRequest carries only ID, Version, IssueInstant, Issuer. No NameIDPolicy, no ACS URL, no Destination (`internal/saml/init.go:39-48`). The IdP answers in its app's configured format; the verifier then demands that the NameID parses as an email (`service.go:294`) and tells the admin when it does not (see section 3, idea 1). Copy: stop sending a format, and put the "must be email" check into a named failure. |
| 8 | Certificate rotation is an outage | PARTIAL | They do not rotate. One cert per connection, compared byte for byte with the cert in the response (`internal/saml/dsig/dsig.go:114-121`). Metadata is fetched once at setup and never refreshed (`apiservice/admin.go:178-215`). The useful part is the recovery UX: on a cert mismatch they store the offending cert (`store/auth.go:298-301`), show Expected and Actual PEM (`authservice/service.go:404-424`, `templates/error.html:78-97`), and the admin flow view offers "if you believe this login is legitimate, set the connection's certificate to the one on this attempt" (`admin/src/pages/ViewSAMLFlowPage.tsx:254-320`). Copy the shape, with a guard: only offer "adopt" when the new cert is not in the metadata URL's set or when the admin is authenticated and sees the fingerprint; never auto-adopt. |
| 9 | Entra empty `mail` | NOT | NameID must be an email or the login is refused (`service.go:425-434`); no UPN fallback. |
| 10 | Entra-initiated SAML logout | NOT | No SLO route exists; the router lists only init, acs, oauth, scim (`service.go:81-101`). |
| 11 | Every failure says the same thing | PARTIAL, best idea in the repo | Typed failure columns on every attempt: bad issuer, bad audience, bad subject id, email outside domains, unsigned, bad signature algorithm, bad digest algorithm, bad certificate, connection not configured (`sqlc/schema.sql:268-282`). The ACS shows a short human line, a flow id as "error code", and a collapsed "Advanced details" with Expected and Actual (`templates/error.html:14-110`). Weaknesses: malformed and expired assertions are a bare `http.Error` 400 and are NOT recorded as a flow (`service.go:260-268`), so the admin sees nothing for those. We must record those too. |
| 12 | IdP's own explanation is discarded | NOT | The SAML Status element is never read (`validate.go` has no Status handling). A non-Success response has no assertion, so it surfaces as "unsigned" (`dsig.go:60-62`), which is misleading. Do not copy. Keep our plan: read StatusCode and StatusMessage and map it. |
| 13 | Directory error copy | N/A | But see the SCIM request log (idea 5). |
| 14 | `hosted_domain` copy blames the user | PARTIAL pattern | Domain mismatch says whose job the fix is: "Subject ID email address is not from the list of allowed domains. This needs to be fixed in the Identity Provider", then lists the allowed domains (`service.go:435-445`). Every message ends "This needs to be fixed in the Service Provider" or "...in the Identity Provider" (`service.go:355-431`). Copy that routing sentence. |
| 15 | SCIM errors collapse | NOT | Unknown, wrong and revoked tokens share one `invalid bearer token` 401 (`scim.go:965`). User create is an upsert, never 409 (`store/auth_scim.go:238`). Group `displayName` uniqueness is deliberately not enforced (`scim.go:491-494`). Ours is better. The log of every call is the thing to copy (idea 5). |
| 16-18 | Setup guides miss provider steps | NOT, but cleaner | Their strategy is to leave the IdP at defaults ("No need to touch any other of the SAML settings", Okta step) and touch only 2 or 3 fields. Fewer fields, fewer errors. They do not mention Force Authentication, group claims or admin consent. Our guides are more complete; borrow only the discipline of "set these N values, leave the rest". |
| 19-20 | Pull scale; expiry tracking | NOT | No expiry tracking of certs or tokens. |
| 21 | Entra SCIM filters we reject | PARTIAL, worse | One unanchored regex `(userName|email\.value) eq "(.*)"` (`scim.go:53`); anything else is a `panic("unsupported filter param")`, a 500 (`scim.go:56`). Two small things to copy: they `QueryUnescape` the value because "scimvalidator.microsoft.com sends url-encoded values" (`scim.go:59-60`), and the last commit added `email.value`. Check whether our parser URL-decodes the filter value. |
| 22-24 | Watch registration, Okta SLO, smaller | N/A / NOT | Nothing. |

Verifier comparison (so nobody is tempted to port their checks): they verify only an Assertion-level signature (Response-level signing returns "unsigned"), only rsa-sha256 and sha256 (`dsig.go:75-91`), no certificate validity period, no Destination, no Recipient, no SubjectConfirmationData NotOnOrAfter, no InResponseTo equality beyond "flow exists and was not redeemed", and NotBefore and NotOnOrAfter are compared with exact `Now`, with no skew allowance (`validate.go:167-175`). The `Validate` doc and tests treat expiry as a pass or fail only. Replay is stopped by a unique `(connection, assertion_id)` constraint (`store/auth.go:328-331`) plus single-use access codes (`store/auth.go:286-296`). Ours covers all of this and more.

## 3. Ideas we do not have, ranked by value

1. **Failure as a record with Expected, Actual and "who fixes it".** Every refusal becomes a row with one typed reason and the offending value, and the page says whether the Service Provider or the Identity Provider owner must act. Files: `internal/authservice/service.go:262-445`, `internal/authservice/templates/error.html`, `sqlc/schema.sql:268-282`, `admin/src/pages/ViewSAMLFlowPage.tsx:160-333`. Fits our P1 #11 and #12 directly, and also fixes our "refused test run is not recorded" gap. Specific copy patterns in section 4.
2. **"If you believe this login is legitimate, set X to Y" remediation line, with "if you do not, do nothing".** The failure doubles as the fix: issuer mismatch offers the received issuer, cert mismatch offers the received cert (`admin/.../ViewSAMLFlowPage.tsx:182-229, 254-320`). Pair with our cert-rotation retry (#8) as the manual path when the metadata URL has nothing new.
3. **A per-attempt flow view that ends the guessing.** One page per login attempt with a timeline: redirect requested (`get_redirect_time`), AuthnRequest sent (`initiate_time`), assertion received (`receive_assertion_time`), code redeemed (`redeem_time`), status In progress, Failed or Succeeded, plus the outgoing AuthnRequest and the incoming assertion as formatted, highlighted XML (`app/src/pages/ViewSAMLFlowPage.tsx:440-540`, columns in `sqlc/schema.sql:256-267`). A stalled timeline tells the admin "the person never came back from the IdP", which is the most common real cause and which our audit JSON cannot show. Caution: when the signature fails, the stored assertion is unverified bytes (`validate.go:98-104`); show it, but label it "as received, not trusted", and redact attribute values by default for non-owner admins.
4. **A test login inside the wizard, with a "what we received" card.** After "assign users", one button runs a real login (`admin/src/pages/SetupSAMLConnectionPage.tsx` Okta assign step ~843-895, `store/admin.go:299-393`). On success it shows the email and every raw attribute name and value in a grid, with two buttons: "Edit connection" (back to the exact field step) and "Setup complete" (`...Page.tsx` test-success card ~895-950). Seeing the real claims is how an admin spots a missing groups claim before it demotes anyone (our P0 #3). Do not copy how they carry the result: email and attributes go through the redirect query string (`service.go:477-488`), which puts claims in URLs and logs. Use a server-side run id.
5. **A SCIM request log.** Middleware records every SCIM call: method, URL, parsed request body, status, response body, and a typed error (bad token, bad username, email outside domains) (`authservice/scim.go:894-1021`, UI `app/src/pages/ViewSCIMRequestPage.tsx:85-183`). Each error has its own explanation and next step, for example "To fix this, give your customer a new bearer token". For us this answers "Okta shows green but nothing happened" without a live probe. Note it records 401s too, which we should keep (rate-limit it).
6. **Real IdP assertion fixtures as a regression corpus.** `internal/saml/testdata/assertions/{adfs,google,jumpcloud,keycloak,okta,ping}` are signed assertions captured from real IdPs, and `bad-assertions/` has one folder per failure (expired early, expired late, bad cert, bad digest, bad issuer, bad audience, bad signature algorithm, no cert, unsigned, invalid UTF-8). `validate_test.go:17-26` runs every folder in the first directory as "must pass". MIT licensed. Importing the six good ones (and the utf8 one) into our `saml-verify` tests gives us ADFS, Ping, JumpCloud and Keycloak shapes we have never seen, for free, without a tenant. Adapt, do not copy blindly: their expiry cases are time-fixed, ours need a frozen clock.
7. **Generic SCIM PATCH as a path interpreter with a quirk list and a table test.** `internal/scimpatch/scimpatch.go:42-131` applies add and replace to a stored attribute tree, handles value filters `a[b eq "c"].d`, creating the element when an `add` filter finds none (`:149-161`), the Entra colon path `urn:...:enterprise:2.0:User:manager` (`:297-335`, documented as non-conformant), capitalised `Add` and `Replace` (`:43-44`), and coerces Entra's `"True"` and `"False"` strings and a bare manager id into `{value: id}` (`authservice/scim.go:821-838`). `scimpatch_test.go` is a 950-line table (names at `:20-884`). We pass Okta and Entra already; use their table to find cases we lack, notably the filtered `add` that creates an array element and the comparison operators gt, ge, lt, le on strings and numbers. They do not support `remove` on users, so we are ahead there.
8. **Setup stepper keyed by sub-step in the URL.** Each IdP has a flat list of 4 to 5 named steps ("Create application", "Configure application", "Download metadata", "Assign users"), and every screen is its own route `/saml/saml-connections/:id/setup/:subStepId` (`SetupSAMLConnectionPage.tsx:156-290`). A sub-step map ties many small screens to one stepper position, so reload and back keep your place, and a link can point at "okta-configure-sso-url". Fits our "admin always knows what to do next".
9. **One-time setup link, 24 h, redeemed into a short session.** (`store/admin.go:121-190`, `admin/src/pages/SetupPage.tsx:25-33`). The page tells you what happened if the link is spent: "you may have used this setup link previously. Setup links expire once you visit them." Environment-level "application name" and "return URL" turn the last screen into "Back to <app>" (`SetupSAMLConnectionPage.tsx:2075-2112`). We already have `setup-links.tsx`; the spent-link sentence and the return button are the pieces to compare.
10. **Rotate-token warning that states the consequence.** "Rotating a SCIM directory's bearer token will break any existing syncs until you input the new bearer token into your identity provider", button "I understand, rotate bearer token", the new token is shown once in a copy box (`admin/src/pages/ViewSCIMDirectoryPage.tsx:91-140, 192-212`). Small, reusable.
11. **Unauthenticated "not fully configured" is a recorded failure, not a 404.** A login that arrives before setup finishes creates a flow marked `error_saml_connection_not_configured` and the developer view says exactly which field is missing (`service.go:170-187`, `app/.../ViewSAMLFlowPage.tsx:226-250`). Useful for the "admin sent the link before finishing" case.

## 4. Their admin setup portal, step by step

Entry: a one-time URL generated by the host app for one organization. Landing page lists that organization's SAML connections and SCIM directories as two cards with a primary create button each and a plain empty state: "Get started by creating a new SAML connection." (`admin/src/pages/IndexPage.tsx:131-291`).

SAML setup (`admin/src/pages/SetupSAMLConnectionPage.tsx`):

1. Choose the IdP. Heading: "What Identity Provider do you use?" Four rows with logo and a one-line subtitle: Okta, Google, Microsoft Entra, Other. Top bar has "SAML Connection Setup" and Cancel (`:306-345`).
2. Top stepper shows the IdP's steps only (Okta: Create application, Configure application, Finish creating application, Copy Metadata URL, Assign users. Google: Create application, Download metadata, Configure application, Assign users. Entra and Other: Create application, Configure application, Download metadata, Assign users) (`:60-152`).
3. Create app. Title "Create an Okta application", one sentence of why ("...that will let you log into our..."), a looping GIF of the exact clicks, then a numbered list of the same clicks, then one button whose label names the next step: "Next: Configure application" (`:534-569`).
4. Configure, one field per screen. For Okta that is name, then "Single Sign-On URL", then "Audience URI (SP Entity ID)". Each screen: what to change, the exact value in a copy box with a copy icon (`ValueCopier`), one guard line ("Make sure 'Use this for Recipient URL and Destination URL' stays checked"), and "No need to touch any other SAML settings" (`:570-682`). Entra splits Identifier (Entity ID) and Reply URL (ACS) the same way (`:1384-1491`).
5. Import IdP data. Okta: paste the Metadata URL. Entra and Google: download the Federation Metadata XML and upload it, with the click path to the download link. Inline zod validation ("SAML Metadata URL must be a valid URL."), Submit, then a success message that names the source and the next action: "Successfully imported your app's SAML settings from Okta. The last remaining step is to assign users to your Okta app." (`:723-842`, Entra `:1492-1632`).
6. Assign users. The only screen with two choices: "Skip testing" (secondary) and "Test SAML connection" (primary). Copy reminds: "If you intend to test the connection yourself, remember to assign yourself too." (`:843-895`).
7. Test. A real login runs. Success card "SAML login successful", subtitle "Here's what we received from Okta", shows "Email (Subject ID)" and every attribute as a name and value tile; buttons "Edit connection" and "Setup complete" (`:895-948`). Failure: the person lands on the ACS error page, not back in the wizard (see section 5).
8. Done. Green check, "SAML Setup Complete", "Back to <application name>" or "Exit this setup page", and a small "Powered by SSOReady" (`:2075-2117`).

After setup the connection page splits two cards: "Service Provider Configuration" ("assigned automatically") and "Identity Provider Configuration" ("assigned by your Identity Provider... need to be copied from your Identity Provider"), a "set up again" link back into the wizard, a collapsed certificate, an Edit dialog, and a "SAML Login Flows" table with Failed, Succeeded, In progress badges (`admin/src/pages/ViewSAMLConnectionPage.tsx:126-300`).

SCIM (`admin/src/pages/ViewSCIMDirectoryPage.tsx`): a read-only page, no per-IdP wizard. It shows the base URL, a "SCIM Authentication" card where the token is viewable only at creation, and Generate or Rotate with the warning above. There are no Okta or Entra SCIM instructions; ours should do better here.

Copy and structure patterns worth borrowing for our UI pass:

- One decision or one value per screen. Every screen ends in exactly one primary button named "Next: <next step>". The admin never has to choose what comes next, except at Test where the choice is explicit.
- Show the click path as a numbered list and as a GIF. The text is the accessible copy; the GIF is for orientation.
- Values we supply are always in a copy box. Values the IdP supplies are always an import (URL or file), never retyped, which removes the whole class of typo failures.
- The failure message pattern, from `admin/.../ViewSAMLFlowPage.tsx:160-333`: first sentence states what the IdP sent ("Your identity provider provided a SAML signature algorithm of X, which we do not accept."), second sentence states the single change ("You need to change the value to RSA-SHA256 in your identity provider."), and the display name is given next to the URI ("often simply displayed as RSA-SHA256"). Third optional sentence for legitimacy: "If you believe this login is legitimate, you need to set the connection's X to Y." The developer-facing variant says "Your customer's IT admin needs to..." (`app/.../ViewSAMLFlowPage.tsx:280-370`), the admin-facing variant says "Your identity provider...". Keep both voices.
- The end-user error page is calm and short, with the technical block collapsed: "Oops, something went wrong! An error occurred while logging you in. Contact your IT admin.", "Error code: <flow id>", then "Advanced Details" (`templates/error.html:8-30`). The flow id doubles as the support handle that opens the flow view. We should keep our current user-facing message and add an error code that deep-links to the admin run.
- Doc links on every field via a tiny `DocsLink` (`app/src/components/DocsLink.tsx`), so each label has its own anchored explanation.

## 5. Things they do worse, or that we should not copy

- Verification is thin: assertion-only signature, one algorithm pair, exact-time conditions with no skew, no Destination or Recipient, no cert validity window, no Status handling, no SLO (see section 2). Our `saml-verify.ts` is the better engine. Do not "simplify" toward theirs.
- Attributes collapse to one string each (`validate.go:139-142`), so groups and any multi-valued claim are lossy.
- Test result passes the email and every attribute in the URL query (`service.go:477-488`), and the success page parses them from `location.search` (`TestModePage.tsx:7-12`). PII in URLs and logs. Use a run id.
- A failed test login ends on a generic ACS page on their domain, not back in the wizard with a next action. Our test-runs view should keep the admin inside setup and say what to fix there.
- Malformed and expired assertions are not recorded (`service.go:260-268`). Our audit trail must cover every refusal.
- Metadata is fetched with `http.DefaultClient` (`cmd/api/main.go:146`, used at `admin.go:186`): no SSRF guard, no size or time limit, no re-fetch. Our metadata fetch must stay guarded. Their cert is pinned at setup and never refreshed.
- SCIM is looser: create is an upsert with no 409 (`store/auth_scim.go:238`), type assertions that panic on bad input (`scim.go:183`, `:584-589`, `:754-755`), unsupported filters panic (`scim.go:56`, `:479`), and many panics are used as error handling in the ACS path (`service.go:448-450`). Do not copy the lax semantics or the panic style.
- PATCH answers 204 with no body (`scim.go:431`, `:765`); some clients prefer the resource back. Ours should keep returning 200 with the resource where we do.
- Group membership PATCH handles only a single operation of a known shape (`scim.go:753-808`); a batched Entra or Okta payload with several operations would fall through. Our group handling is broader.
- One shared message for all token failures and no revoked or expired state (`scim.go:965`).
- No expiry tracking, no alerts, no group rules, no SCIM-vs-JIT story; the portal has no per-IdP SCIM instructions.
- Setup assumes the admin has a browser session with the IdP console in another tab and shows no screenshots for current UI of Entra or Okta in text form; the GIFs will age with the vendors. Keep our text-first steps and treat any visuals as optional.
