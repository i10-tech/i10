## 3. Top findings, ranked

### 1. HIGH: a partial Directory answer is believed, then everybody missing is deprovisioned (D4, D5, scenario 21 and 22)

`pullGoogleDirectory` refuses only an empty list (google-directory.ts:1044-1048). Two ways to get a non-empty but short list without an error: (a) `domain=` restricts to ONE domain, so people on a secondary domain or renamed to one are "missing" (documented behaviour of the `domain` parameter); (b) an impersonated admin with an OU-scoped admin role (INFERRED: Admin roles are assignable to an OU scope) sees only that slice. The pull then deletes every other person through `deleteUser` (outbox, deprovisioning). Design note 2.19 already lists "a cap on how many people one pull may delete" as open. Fix: (1) drop `domain`, list by `customer=my_customer` and filter by the proved domains in code (and keep secondary-domain people whose primary is proved); (2) verify at check time and before every pull that the subject is a super admin with `users.get(adminEmail)` field `isAdmin`/`isDelegatedAdmin`; (3) a hard guard: refuse (`suspicious_shrink`) when more than ~20% or more than N of existing live people would be deleted, requiring an owner confirmation to proceed.

### 2. HIGH: SAML rename locks the person out with no way back (S4, scenario 4)

Google's default NameID is the primary email, and a rename changes it. `subjectOf` makes `email:<new address>` a new subject; `resolve` finds the OLD identity row on the same Clerk user and returns `already_linked` (bridge.ts:962-966). The person gets the generic message and an admin has no unlink action (no route found). The Google preset's text says the account "moves" (saml-presets.ts:152), which is the opposite of what the code does. Fix: for a Google SAML connection default `subjectAttribute` to something immutable (Google can map a custom attribute; there is no immutable built-in) or, safer, treat an `already_linked` whose old subject is the same NameID format and whose directory row/externalId matches as a rename: re-point the identity to the new subject after a fresh verified-email check. At minimum add an owner action "Relink this person" and give `already_linked` a distinct message ("Your sign-in address changed. Ask your administrator to relink you."). Correct the preset text and add a test for the rename.

### 3. HIGH: "Require MFA" and step-up cannot work on a Google connection (O7, S16, scenarios 10 and 11)

Google ID tokens carry no `amr`, `acr` or `auth_time` (from the claim list in Google's OIDC page); the SAML preset has no MFA context mapping for Google. The console lets any connection set `mfaRequired` (identity.ts:230-234, access-panel.tsx:268-276), and bridge.ts:450 then refuses every non-exempt sign-in, forever, with a message that tells the person to do something they cannot do. Step-up (bridge.ts:1062-1068) fails closed for the same reason. Fix: refuse to enable `mfaRequired` on a Google OIDC/SAML connection in the API (422, "Google does not tell us whether a second factor was used. Enforce 2-Step Verification in the Google Admin console instead."), grey it out in the UI with the same sentence, and say in the preset that step-up for managed Google accounts is unavailable (or fall back to an email code for them).

### 4. MEDIUM-HIGH: directory failures give the customer the wrong next action or none (D3, D17, D18, D19, scenarios 13-18, 26)

`classifyApiFailure`/`classifyTokenFailure` collapse "subject not an admin", "Admin SDK API off in OUR project", "bad JWT/clock" and "delegation missing" into `unauthorized_client` (google-directory.ts:243-315). The console knows copy for two of twelve codes (directories-panel.tsx:57-61) and prints the raw code in the status line (line 242). `directory.sync_failed` is audit only. Fix: split the codes (`not_admin` for 403 reason `forbidden`, `internal_misconfig` for `accessNotConfigured`/bad JWT, which must page us, not tell the customer anything), add a message per code with the next step ("Authorise client id X with exactly these scopes, then wait up to 24 hours" / "Use a super admin"), show them in the status line, and send the same alert path the SAML cert expiry uses when a pull has failed for more than an hour.

### 5. MEDIUM: pull cannot finish for large directories (D12, D13, scenario 23 and 24)

Group members are fetched one group at a time with no pacing (google-directory.ts:~862-893) inside a 180 s job timeout (google-directory-queue.ts:66); limits allow 2000 groups. There is no in-request backoff for 403/429/5xx, so one transient 503 in a 10-minute pull discards all work. Fix: bounded concurrency (4-8) for members calls, per-request retry with Google's recommended exponential backoff (2^n s plus jitter, up to n=5), raise the job timeout to match the bounds, and record `timeout` as its own code.

### 6. MEDIUM: Google SAML and OIDC setup text omits what a Workspace admin must do and what blocks users (S6, S11, S12, O10, scenarios 1, 2, 9)

`requires` for SAML Google (saml-presets.ts:148-153) lacks: turn the app ON under User access for the right OU/group (up to 24h), group mapping rules (75 groups, only selected ones are sent), Start URL, and the IdP-initiated option. The OIDC Google text says "Nothing at Google" (oidc-presets.ts:125, idp-setup.tsx:178) although Workspace admins can block third-party apps and then must allowlist our client id. Add a troubleshooting block that names Google's own errors (app_not_configured_for_user = Entity ID case-sensitive match or app OFF; app_not_enabled_for_user; access blocked by admin policy) since they never reach us.

### 7. MEDIUM: `hosted_domain` refusal is the wrong message for a real Workspace member (scenario 8)

The message always says "not a personal one" (model.ts:331).
