## Generation and schema derivation

The generator enumerates the tables touched by the registry in the migrated `core`, `identity`, and `authd` schemas. It reads `pg_catalog` for column types, nullability, varchar limits, primary and foreign keys, CHECK constraints, and partition bounds. The catalog is authoritative for the installed schema; the definitions originate in `apps/api/src/db/schema.ts` and its imported schema modules. Candidate types are selected from those facts: nullable values only for nullable columns, strings only for text-like types, JSON variants only for `jsonb`, numeric edges only for supported numeric types, and timestamp extremes or partition boundaries only for timestamp columns. Status/kind candidates are limited to free text columns without a CHECK or enum constraint. Logical-parent orphans are attempted only when no FK protects the relationship.

Every eligible column in the small seed is attempted; there is no column sampling. Updates use savepoints, so a database rejection rolls back only that candidate and records the reason as schema protection. Accepted candidates for a table-column pair land on distinct source rows. Tenant tables prefer rows from the huge and median tenants, the SSO tenant, and fixture tenants. Authd tables prioritize accounts, domains, and fixture values used by registry pickers. Remaining rows use deterministic offsets. The accepted corpus contains 1,550 candidates across 506 unique row keys. There were no duplicate accepted row keys within a table-column pair. The full pass took 8.2 seconds.

## Findings ranked by risk

1. **Medium, chaos-only wrong answer: group address lookup loses a fixture team inbox.** `authd.groups_by_address`, case `address stored with capitals`, failed its explicit expectation after chaos. The nullable `authd.groups.email` candidate set the fixture row's email to null. Exact final row: `authd.groups(name="fixture-support", email=null, tenant_id=null, created_at="2026-11-23T13:31:27.588484+00:00", description=null, directory_group_id=null)`. The nullable `email` candidate removes the address the case looks up; a separate accepted nullable candidate also clears `tenant_id` on the same row. The lookup returns no team inbox, which can break address-to-group resolution. The database permits both nulls; the application path and this registry expectation require a populated email.

2. **High, pre-existing wrong answer: mixed-case alias lookup returns no mailbox.** `authd.accounts_by_address`, case `alias stored with capitals`, failed on both normal and chaos seeds. Trigger: `authd.aliases(address="Sales@mixedcase.example", clerk_user_id="user_fixture_mixed-case", source="console")`. The read path lowercases the lookup but compares the stored alias directly.

3. **High, pre-existing wrong answer: mixed-case suppression does not suppress.** `send.suppressed_for`, case `suppression stored with capitals`, failed on both seeds. Trigger: `core.suppressions(tenant_id="00000000-0000-7000-8000-000000000002", address="Bob@Example.test", reason="manual")`. A send to `bob@example.test` is not blocked, so a previously bounced or complained-about address can receive mail.

4. **Medium, pre-existing wrong answer: mixed-case verified domain is not sendable.** `send.sendable_from`, case `domain stored with capitals`, failed on both seeds. Trigger: `core.domains(id="00000000-0000-7000-8001-000000000001", tenant_id="00000000-0000-7000-8000-000000000002", name="MixedCase.Example", status="verified", hosts_mailboxes=true)`. The send gate compares the stored name with a lowercased value.

There were no SQL errors across 147 measurement statements. The normal control had three explicit expectation failures; chaos had those same three plus the chaos-only group finding. Plan shapes changed for a small number of statements, mainly lookup/index choices on small tables; the final chaos run added no plan warning. The existing partition-probe warnings remained. Plan timing differences on this small seed were not material or stable enough to treat as regressions.

## Reproduction and verification

From `apps/api`, use only the dev scratch:

```sh
bun scripts/scale/cli.ts up --scratch dev
bun scripts/scale/cli.ts seed --scratch dev --profile small --seed 7 --anchor 2026-11-20T12:00:00Z
bun scripts/scale/cli.ts measure --scratch dev --runs 1 --out /tmp/db-scale-normal-measure
bun scripts/scale/cli.ts reset --scratch dev
bun scripts/scale/cli.ts seed --scratch dev --profile small --seed 7 --anchor 2026-11-20T12:00:00Z --chaos
bun scripts/scale/cli.ts coverage --scratch dev --seed 7
bun scripts/scale/cli.ts measure --scratch dev --runs 1 --out /tmp/db-scale-chaos-measure
bun scripts/scale/cli.ts down --scratch dev
```

The flag-off byte-for-byte test compares normal seed row fingerprints with and without the `chaos: false` option. Required checks on this implementation run: `bun test test/scale-scrub.test.ts test/scale-plan.test.ts`, `DB_SCALE_TEST_PORT=55511 bun test test/scale-generator-db.test.ts`, `bunx turbo run lint check-types --filter=@i10/api`, and Prettier on changed files.
